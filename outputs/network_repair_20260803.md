## 확정된 메커니즘 두 가지

### (a) 유효 배정 지점이 VRD 표식 위치가 아니다

`combineStaRoutDec="true"` 이면 상류 경로가 끝나는 지점에서 다음 경로결정이 이어 붙는다.
link 68 상류 경로결정(1123-2 / 1124-1 / 1125-1)의 목적지가 link 68 안쪽에 있어서,
차량은 표식이 @98.802 에 있어도 훨씬 상류에서 이미 route 1135-x 를 지닌 채 분기 10681 을 만났다.

여기에 `lnChgDist` 가 겹친다. 차량은 목표 커넥터 앞 `lnChgDist` 구간부터 차로를 잡는데,
route 2 의 목표 10646(@352.004)에 대한 조준 시작점이 분기 10681(@76.589)보다 하류였다.
조준을 시작하기도 전에 분기를 만나 쓸려 나갔고, link 2 에 올라가 자기 경로의 10646 을
영영 못 만난 채 link 2 끝에서 삭제됐다.

위치제약 도달성 탐색으로 확인했다 — VRD 위치에서 10646 을 거치지 않고 link 2 에 가는 길은 없다.
즉 삭제된 차량은 **경로를 이탈해** link 2 에 올라간 것이다.

### (b) 착지 차로가 전부를 가른다

link 71 은 82.6 m 인데 커넥터 10635 는 lane 4~5 에서 출발한다.
link 70 은 2 차로뿐이라 커넥터 10641 이 link 71 lane 1~2 에 떨어뜨렸고,
차량은 80.9 m 안에 3 개 차로를 건너야 했다. VRD 를 상류로 옮겨도(3 차),
`lnChgDist` 를 1000 으로 키워도 소용없었다 — 진입 시점에 이미 lane 1 이기 때문이다.

| 진입 커넥터 | 착지 차로 | 10635 까지 건널 차로 | 삭제 (런 평균) |
|---|---|---:|---:|
| 10640 (link 69) | lane 4~5 | 0 | 1.9 |
| 10641 (link 70) — 수정 전 | lane 1~2 | 3 | 30.2 |
| **10641 — 수정 후** | **lane 2~3** | **1** | **6.0** |

착지 차로를 한 칸 올린 것만으로 link 71 삭제가 60.7 → 14.9 로 떨어졌다.

## `lnChgDist` 1000 은 지체를 악화시키지 않았다

커넥터 770 개를 200 → 1000 으로 올린 것이 인위적 대기행렬을 만들 것을 우려했으나,
실측은 반대다. 평균 지체 −1.4 %, 평균 속도 +1.0 %, **총 정지횟수 −33.4 %**.
차로를 미리 잡으니 붙었다 섰다 하는 차선변경 발버둥이 줄었다.
일반 링크 448 개는 200 을 유지하고 있다.

단, 지체·속도는 잔류 차량 처리 방식에 따라 편향될 수 있다.
정지횟수가 그 편향에 덜 취약해 상대적으로 신뢰도가 높다.

### 차량 수지 — 닫힌다

평가 시작을 0 으로 놓아 워밍업 도착을 포함시키고 1 런(seed 13)씩 재측정했다.

```
총 투입수요 (0~4500 s) = 25,574.5 대

원본:  VehArr 22,257 + VehAct 3,165 = 25,422      잔차 152.5 (0.6 %)
최종:  VehArr 22,283 + VehAct 3,139 = 25,422      잔차 152.5 (0.6 %)
```

양쪽이 소수점까지 같다. 수지는 닫힌다.

앞서 "679.6 대 불일치" 라고 적었던 것은 **이중계산이었다.**
VISSIM 의 `VehArr` 는 "망을 떠난 차량" 이므로 **삭제된 차량까지 포함한다.**
거기에 삭제를 별도 손실항으로 다시 더한 것이 원인이다.

수지를 분해하면 이번 수리의 실질이 드러난다.

| | 원본 | 최종 |
|---|---:|---:|
| 망을 떠난 차량 (VehArr) | 22,257 | 22,283 |
| ├ 삭제로 떠남 | ~821 | ~129 |
| └ **목적지 도착으로 떠남** | **~21,436** | **~22,154** |
| 망내 잔류 (VehAct) | 3,165 | 3,139 |

**런당 약 718 대가 사라지는 대신 통행을 완주한다.**

`Net.Vehicles.Count` 는 `RunContinuous` 종료 후 0 을 반환한다(VISSIM 이 망을 비운다).
잔류는 `VehAct` 로 읽어야 한다.

## 도구

`scripts/audit_static_routes.py` — 정적경로가 위치제약을 지켜 완주 가능한지 전수 감사한다.
링크 위에서는 상류→하류로만 가므로, 경로가 요구하는 커넥터가 진입점보다 상류면 완주 불가이고
VISSIM 은 링크 끝에서 차량을 삭제한다. GUI 에서 커넥터 끝점을 몇 미터 끄는 것만으로 생기며
눈으로는 보이지 않는다. 실제로 이번에 1.837 m 어긋난 VRD 1126 을 잡아냈다.
종료코드가 0/1 이라 파이프라인에 물릴 수 있다.

```
python scripts/audit_static_routes.py network/real_world_gaepo_modi/modi.inpx
```

## 주의

- **이전에 잡은 기준선·캘리브레이션은 전부 무효다.** 다만 이유는 혼잡도 증가가 아니다 —
  잔류 차량은 3,165 → 3,139 로 오히려 줄었고 지체도 −1.4 % 다. 망은 추가 부하를 무리 없이 흡수했다.
  무효인 이유는 **유동 패턴이 바뀌었기 때문**이다. FW_E 가 런당 278.9 대를 잃던 것이 0 이 되었으므로
  그 구간의 유량·밀도 관계 자체가 달라졌고, FD 적합값(`v_free`, `rho_crit`)은 옛 관계 위에서 맞춰져 있었다.
- VISSIM `.err` 는 BOM 없는 CP949 다. UTF-16 을 먼저 시도하면 바이트 길이가 짝수인 파일에서
  예외 없이 디코딩에 "성공" 하면서 모지바케가 되고 집계가 조용히 0 이 된다.
- 링크 통과량은 COM 링크 속성(58 개)에 `Vol` 계열이 없어 이 경로로는 못 뽑는다.
  커넥터별 분담률이 필요하면 링크 세그먼트 결과 파일을 읽어야 한다.
