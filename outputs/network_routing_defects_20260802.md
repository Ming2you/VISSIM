## C. 선행 진단의 정정

앞선 조사 보고는 이렇게 적었다 — *"route 1135-2 를 배정받은 차량 일부가 커넥터 10681 로
FW_E 본선에 올라타 link 2 끝에서 삭제된다."* **이 인과 설명은 성립하지 않는다.**

수정 전 기하에서 커넥터 10681 은 link 68 @ 76.589 이고 VRD 1135 는 @ 98.802 였다.
10681 로 빠진 차량은 pos 98.802 에 도달하지 못하므로 route 1135-2 를 배정받을 수가 없다.
실제로 `.err` 에서 VRD 1135 는 "차선변경 대기 강제제거" 에도 "경로결정 무시" 에도
한 건도 나오지 않는다 — 차량은 정상적으로 경로를 받았다.

## D. 상대유량에 대한 오진 — 취소한다

이 절은 원래 *"VRD 1135 의 route 가 전부 `relFlow=""` 이므로 유량이 0 이고, 그래서 수정이 무효다"*
라고 적었다. **틀렸다.** `relFlow=""` 는 0 이 아니라 **기본값 1.000** 이다.
사용자가 VISSIM GUI 에서 세 route 모두 1.000 으로 표시되는 것을 확인했고,
네트워크의 다른 VRD 도 같은 규칙을 따른다 (VRD 1126 은 전 route 가 `""` 인데 정상 배분되고,
VRD 1133 은 r3 만 값이 있고 r1/r2 가 `""` 인데 r1/r2 도 배분된다).

따라서 수정 전 분배는 route 2 / 3 = 50 : 50, 수정 후는 route 2 / 3 / 4 = 33 : 33 : 33 이다.
route 4 는 처음부터 활성이었다.

## E. 확정된 메커니즘

`combineStaRoutDec="true"` 때문에 **유효 배정 지점이 VRD 표식 위치가 아니다.**
link 68 상류 경로결정(1123-2 / 1124-1 / 1125-1)의 목적지가 link 68 안쪽에 있어서,
앞 경로가 거기서 끝나는 순간 VISSIM 이 VRD 1135 를 이어 붙인다. 즉 차량은 표식이 @98.802 에
있어도 그보다 훨씬 상류에서 이미 route 1135-x 를 지닌 채 분기 10681 을 만난다.

여기에 `lnChgDist` 가 겹친다. 차량은 목표 커넥터 앞 `lnChgDist` 구간부터 차로를 잡는데,
route 2 의 목표 10646(@352.004)에 대해 조준 시작점이 분기 10681(@76.589)보다 하류였다.
조준을 시작하기도 전에 분기를 만나 1~2 차로 차량이 쓸려 나갔고, link 2 에 올라가
자기 경로의 10646 을 영영 못 만난 채 link 2 끝에서 삭제됐다.

20 런 페어 실측으로 확정했다 — 상세는 `outputs/vrd1135_ab_20260803.md`.
freeway 체인 삭제 런평균 278.2 → 25.8 (−90.7 %), 20/20 런 개선.

## G. 방법상 주의 — .err 인코딩

VISSIM 이 쓰는 `.err` 는 BOM 없는 **CP949/ANSI** 다. UTF-16 으로 먼저 시도하면 바이트 길이가
짝수인 파일에서 예외 없이 디코딩에 "성공" 하면서 CJK 모지바케가 되고, 집계가 조용히 0 이 된다.
BOM 을 검사해 없으면 CP949 로 확정해야 한다.
