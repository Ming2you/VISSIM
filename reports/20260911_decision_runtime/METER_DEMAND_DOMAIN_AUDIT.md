# 미터 수요와 탐색 영역의 읽기 전용 진단

저장 상태 1050초/실제 이전 명령 900초를 확인했다. 새 모델 예측이나 COM 실행은 하지 않았다. **높은 all-open 표시값 주위에서 미터가 움직이지 못한다는 지적이 맞다.** 다만 수요 근처에 요청값을 넣는 것만으로 모두 해결되지는 않는다.

`vissim_stackelberg_adapter.real_world_ramp_meter_write_back`의 수요 힌트는 connector별 마지막 완료 링크평가 유량과 과거 힌트다. 대기 차량, 목적지별 희망 수요, 미래 도착 예측은 이 계산에 들어가지 않는다.

`h_m = max(v_m, k_m h_prev,m, 150)` [veh/h]. 이전 미터가 10초 모두 녹색이면 k=0.9, 구속 중이면 k=1이다. 관측 v는 runner `FarMeasurementJson()`의 `AVG:LinkEvalSegs\\Volume(Current,Last,All)`이며 실제 도착 의향과 같지 않다. 막힌 접근로/차로에서 통과하지 못한 수요는 관측 유량에 나타나지 않는다.

기존 allocator는 `f_m(g)=min(3600×lanes_m×n(g)/10, h_m)`, `D_open=Σf_m(10)`을 사용한다. 요청 r≥D_open이면 모든 해당 SG를 10초 녹색으로 하고, canonical 처리에서는 그룹 표기를 1800으로 되돌린다.

| 그룹 | D_open [veh/h] | 현재 고정 요청 범위 |
|---|---:|---:|
| R_D_W | 494.374 | 1500–1800 |
| R_F_W | 852.053 | 1500–1800 |
| R_D_E | 412.135 | 1500–1800 |
| R_F_E | 366.000 | 1500–1800 |

따라서 모두 같은 all-open 물리 명령이다. 다음 실제 step에서도 적용값이 1800이면 같은 박스가 생긴다. 1500→1200으로 누적해서 내려갈 수 없다. fixed-coordinate proof는 이 사실만 증명하며 미터 제어 전체가 불필요하다는 증거가 아니다.

추가로 정본 `_measured_meter_allocation`만 호출했다. DW/DE/FE는 각 h가 최소 양의 녹색 2초의 처리량보다 작다. 양의 모든 녹색에서 예측 유출이 같고, 폐쇄 벌점과 긴 녹색 우선 동률 규칙 때문에 요청을 100까지 내려도 10/10초를 고른다. 아주 낮은 요청에서만 `close_below_frac`가 0/0초로 바꾼다. FW는 0.99×D_open 요청에서 10/3초, 0.8×D_open에서 3/3초가 된다. 이는 요청 영역 문제와 수요로 잘린 전달함수의 평탄부가 함께 있음을 보인다.

단위를 분리해야 한다. 그룹 r=1800은 두 물리 미터를 묶은 모델 값이다. CSV의 각 `rate_vph=900×green/10`은 writer 일관성 부호화이며 실측 유출이 아니다. 표의 포화 서비스는 10초 녹색에서 차로당 1512veh/h로, 위 900과도 다르다. N_UF는 현재 그룹 표기 합이므로 all-open7200을 실제 도착/통과량으로 읽으면 안 된다.

±300은 사용자가 명시한 숫자가 아니다. `joint_decision_move_limits()`의 새 hardcode, `joint_owner_neighbors`와 vendor `wu_faithful_follower.py:3303`의 기존 baseline box, 별개의 가격 차분 δ300/신뢰영역0.20에서 왔다. 사용자 요구는 **실제 이전 행동에 고정된 변경 제한, 같은 decision에서 중심·폭 불변**이다.

권고는 실제 명령 `(SG별 green, cycle)`을 기준점으로 보존하고, 다음 실험부터 고정된 물리 변경 규칙을 먼저 정하는 것이다. SG별 ±1초 녹색은 해석이 명확한 후보이나 새로운 제어 조건이며 순수 속도 개선으로 보고하면 안 된다. 포화 서비스 ±300을 쓰려면 `μ(g)`의 측정·차로별 단위를 확인하고 post-quantization에서 검사해야 한다. 현재 표상 10→9초는 차로당183.6veh/h, 2차로는367.2veh/h이므로 ±1초와 ±300은 같지 않다. 현재 demand-capped 그룹값 1800을 관측 h로 재명명해 박스를 옮기는 방식은 금지해야 한다.

수요·queue-aware 값은 후보의 우선순위를 정하는 데 쓰고, 실제 고정 물리 박스와 교집합을 취해야 한다. 원점/목적지 희망 수요, 접근 도착, 대기열을 별도로 구분한다. `도착률 + 대기차량/예측구간`은 처리 필요량 힌트이지 과거 실제 명령이 아니다. 물리 박스 안의 9초 명령도 allocator가 10초로 덮어쓰면, 기존 helper에서 명시적인 물리 스케줄을 보존하는 작은 확장이 필요하다. grouped 예측이 그 서비스 차이를 표현하는지는 별도 동일명령 native 검증이 필요하다.

필수 검사: (1) 같은 물리 all-open 요청 별칭은 동일 명령, (2) 실제10초→허용9초가 양자화 후에도 유지, (3) 다음 step 기준점은 실제9초, (4) 낮은 통과유량+큰 대기열을 낮은 희망 수요로 오인하지 않음, (5) 비대상 connector 명령 불변, (6) spillback 개방 강제와 상충하는 후보는 실패, (7) rate·포화서비스·관측유출·N_UF 별도 기록, (8) 변경 전후 짧은 LSA와 FZP로 실제 전환·방출 비교.

## 실제 짧은 실행으로 확인한 범위

고속도로80%·도시50%·seed13의 같은 정본 실행에서 900초까지 FZP 939,081개 행이 정확히 같은 두 실행을 비교했다. 900–1050초 동안 RM_C10646/10644 두 곳만 녹색10→9초로 변경했다. 다른 미터·도시 신호·VSL·수요·경로는 유지했다.

- writer에서9초 명령이 다시10초로 바뀌지 않았고 실제 LDP/readback도 일치했다. 실제 신호는 **9초 GREEN+1초 AMBER, RED0초**다.
- 각 connector의 관측 진입은21대, 정지선 통과와 고속도로 합류는 각각20대로 두 실행이 같다. g9의 황색에10646에서1대,10644에서3대가 통과했다. 명령 CSV의810veh/h를 실측 용량으로 읽을 수 없다.
- 이후102대의 궤적이 달라졌지만 이150초의 ΩTTT·TTD는 같았다. 초반 한 구간·한 seed이며 첨두 수요나 전체 효과를 식별한 결과가 아니다.
- LSA의 COM 사건 누락은 두 실행 모두 독립 FAIL이다. LDP로 실제 전환을 확인했지만 사용자가 요구한 LSA 완전성을 충족했다고 하지 않는다.

따라서 수요 근처를 탐색해야 한다는 방향은 맞지만, 올바른 순서는 **목적지별 접근 도착과 정지 대기열을 확인 → 그 서비스 수준에 대응하는 실제8SG 녹색 후보 생성 → 직전 실제 명령에 고정된 물리 변경 한도 검사 → 신호/방출/대기열 검증**이다. 통과하지 못한 수요를 누락하거나, 주행 중인 램프 재고를 모두 정지 대기열로 더하면 안 된다. 현재 forecast에 이미 queue/drain 환산이 들어간 경우 다시Q/H를 더하면 중복이다.

8개 녹색을 전략으로 올리려면 소유권·후보·고정 박스·가격·writer를 함께 연결해야 한다. 현재 모델은4개 그룹 서비스만 읽고1800cap을 적용하므로 g10/g9가 같은 모델 값이 될 수 있다. 실제 두 branch의 도착/대기 위치 없이 그룹 재고를 임의 분할하거나 용량을 줄여 가짜 감도를 만들지 않는다. 이번 진단 helper와 실제 실행은 명령 보존을 확인한 단계이며 **활성 follower game의 미터 영역과 branch 모델이 해결된 상태는 아니다**.
