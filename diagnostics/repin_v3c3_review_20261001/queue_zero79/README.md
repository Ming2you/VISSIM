# REVIEW79 — 관측된 큐 0과 누락을 구분

2026-10-03. 별도 DATA9000의 4050초 초기화 실패를 저장 관측으로 재현하고, 기존 위치 기반 도착 모델의 투영을 수정했다. VSL 계수·물리 모델·현재 동결된 native 비교는 바꾸지 않았다. 전체 목표는 ACTIVE / NOT_QUALIFIED이며 실패한 9000초 런을 재시작하지 않았다.

Claude 기록을 먼저 확인했다. `upstream_worklog/02_urban_b2/diag_c3_r2/U7.md`의 §1.1은 연속 큐 항목이 없으면 전체 정지 차량으로 되돌아가는 기존 투영을 설명한다. 현재 오류에 대한 적용 완료된 수정은 아니므로 그대로 정답으로 채택하지 않았다.

## 확인한 원인과 수정

4050초 link66의 차량은195대, 정지 차량은129대였지만 정지선 연속 큐는0대였다. 선두가 움직이거나 정지선에서 떨어져 있어 연속 walk가0을 내는 상황이다. 기존 함수는0 항목을 생략했고, 원래 투영은 이를 관측 누락으로 간주해129대를 즉시 방출 가능한 movement queue로 배정했다. 뒤의 위치 기반 초기화는 같은 관측에서0을 얻어 불일치 오류를 정확히 검출했다.

기존 kinematic contract에 지정된 링크에서만 관측0을 보존한다. 현재 적용 링크는66이다. 계약 망 SHA, complete vehicle frame, queue bin의 전체·정지 차량 수를 먼저 확인한다. 관측 누락을0으로 바꾸지 않고, 기존 초기화의 불일치 검사도 유지한다. 다른 링크의 투영, 도착시간 식, 제어 주기, 수요, 계수는 그대로다.

변경한 정본 파일은 `observation_projection.py`, `runtime_setup.py`, `vissim_stackelberg_adapter.py`다. 기존 진단 driver에3900/4050초 저장 상태 초기화만 허용했고, `probe.py`는 정본 초기화를 호출하며 원본 관측 캐시의 바이트 일치만 검사한다. 새 runner/adapter는 만들지 않았다.

## 검증 결과와 한계

- 수정 전4050초는 같은 ProjectionError를 재현했고, 수정 후 전체 초기화가 통과했다.
- link66은195대를 모두 유지한다. 즉시 큐129→0, 접근 중 재고66→195로 바뀐다. 위치 기반 도착/저류해제 예약은 각각195대, 마지막 도착 지연은224초다. 미래 교통을 입력하지 않았다.
- 전체 관측 투영의 도시 차량 장부는3117→3117대다. 다른 링크 장부·큐·예약은 정확히 같다.
- 직전 정상3900초는 수정 전후 초기화 직전·직후 상태와 kinematic metadata가 정확히 같다.
- 새 관측0/누락 검증12개와 기존 잔여정지5·head17·상류준비8·kinematic11개, 총53시험이 통과했다. 원래 큐 불일치 검사가 잘못된 상태를 계속 거부하는 시험도 포함한다.

`initialization_assessment.json`과`assess.py`에 증거와 SHA를 저장했다. `urban_link_storage`는 점유 재고가 아니라 **남은 수용공간**이다. 첫 임시 assessment는 이를 큐에 더해 잘못된 보존 검사를 하다가 실패했다. 수정한 진단은 물리 장부 합계와 `−수용공간 변화 + 큐 변화 =0`을 확인한다. 이 진단 오류 때문에 생산 코드를 바꾸지는 않았다.

이번 검증은 저장 상태의 초기화까지다. 수정 후4050초 자율 예측·SDMPC 선택·native 실행이 통과했다고 확대하지 않는다. 신규 예측0회·VISSIM0회·FZP 재스캔0회·push0회다. 기존 STOP SHA91b2163b…를 확인했다. 실행 중인 REVIEW78은 수정 전 별도 동결본을 사용하므로 이 변경의 영향을 받지 않는다.

## REVIEW80 — 수정 후 450초 자율 예측까지 확인

다음 목표 턴에서 실패했던4050초 저장 상태의 실제 직전 명령을 유지해450초 예측했다. 기존 driver의 held450 모드를 재사용하고, 관측/head/VSL 이력은4050초까지만 썼다. 성공한 예측의 계산 시간은29.956초다. 모든 저장 상태(4050/4200/4350/4500)의 물리 재고 장부가 통과했고,8램프의 보존 잔차 최대2.52e−13대·자원 한도 초과 최대1.24e−14대였다. link66의195대 초기 도착 예약은4200초51대,4350초0대가 남아 원래 도착시간에 따라 처리됐다. 차량 삭제로 오류를 피하지 않았다.

진단 보조 코드에서 두 번 실패했다. 첫째는 낮은 우선순위 설정에 쓰는Windows HANDLE의64비트 형 선언 누락으로 예측 전에 종료됐다. 둘째는450초 예측 후 장부 응답을 첨부하기 전에 진단 훅이 읽어 종료됐다. 형 선언과 훅 설치 시점을 수정하고 원본 실패 로그를 보존했다. 실제 예측은 실패한 응답 수집1회와 성공1회, 총2회였으며, 최적화·새VISSIM·계수 보정은0회다. `rollout_assessment80.json`과`assess_rollout80.py`가 검증 결과다.

이 결과는 예측 실행과 보존 검증이다. 실패 런에는4050–4500초 실측이 없으므로 정확도·이득 검증으로 부르지 않는다. 기존9000초 런은 재시작하지 않았다. REVIEW78은 별도 동결본으로 계속 실행 중이며, 첫selected는3150초 정상종료/1021초, 두번째vsl90은2979초 실제진행과 소유cscript48704/VISSIM43540 생존을 확인했다. 두번째 종료 전에는FZP 분석을 시작하지 않았다.

## VSL 판단은 독립적으로 유지

사용자는 Claude의 VSL 해석도 틀릴 수 있음을 다시 지적했다. Claude 기록은 선행 진단 확인용이지 모델의 정답이 아니다. REVIEW76에서 실제 Ω VSL 이득−2.065대·시간에 비해 예측은−0.0488이었으므로 물리 반응이 충분히 보정됐다고 할 수 없다. REVIEW77의 다른 RM·도시 명령에서는 모델이 VSL90의 손해+0.5576을 예측했다. 이를 확인할 동일 RM·도시 명령의 VSL110/90 대조(REVIEW78)가 진행 중이며, 두번째 arm 실행 상태까지 확인했다. 두 런 종료·소유 프로세스 종료 후 기존 postprocess plan으로 실행 검증과 손익을 확인한다. 현재는 실제 손익 미확정이다.
