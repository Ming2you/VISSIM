# 무제어 수요 탐색 우선 전환

최신 결과: 빠른 native5400초 수요 탐색을 완료하고 **고속도로 원점70%·도시 원점30%, seed13**을 첫 제어 비교 조건으로 선택했다. 상세 근거·한계·설정은 `demand_sweep/DECISION_20260910.md`, 기계 판독 선택은 `demand_sweep/selection.json`에 있다. 아래의 '다음'과 '실행 중' 표현은 그 시점의 역사 기록이며 현재 백그라운드 sweep은 실행 중이 아니다. controller/GNE/리팩터링은 보류 상태다.

사용자 지시에 따라 controller 개선, 계산 추적, 반복 예측 및 배경 전수 분석을 보류했다. 완료된 코드 수정과 유효 결과는 보존한다.

## 실행 정리

- r03의 기준망은 유효한 r02 5400초 결과를 재사용했다.
- r03 LCD10635 1000→2000m 런은 5400초, exit 0으로 완료됐다. 완료 자체를 개선 효과로 해석하지 않는다.
- 뒤이어 시작한 r03 upstream1135 런은 사용자 우선순위 변경으로 중단했다. 실행 실패나 교통 정체 결과로 분류하지 않는다.
- 명령, 부모 PID, 생성 시각을 확인한 소유 프로세스 43860 / 40800 / 41836 / 28256만 종료했다. 확인 기록은 `no_control_network_arms/r03/interrupted_owned_processes.json`에 있다. 기존 manifest 및 부분 결과는 보존한다.

## 수요 탐색 기준망

`fixed_beta300v3_network_arms_flat_v1/baseline.inpx`

SHA256: `085a10c71874e897083c97097af8fa3f1f08da1ef7416fef2f7cfbedabdfc317`

원망과 물리 link 및 파일 바이트가 같다. 이번 sweep에는 LCD 확대, upstream1135 경로 확장, 차로 연결 변경을 포함하지 않는다. 기존 native 신호 42개, VSL 120 km/h, 물리 metering 8개 상시 GREEN 조건을 고정한다. 새 controller 모델 설정은 사용하지 않는다.

상류 경로 실험은 별도 보존한다. 그 실험에서는 downstream decision1135와 그 경로를 삭제하고 1123/1124/1125로 분할 경로를 확장했으므로 1135 중복은 없다. 그러나 66→68은 여전히 차로4 진입이고, 뒤의 10681은 68 차로1–2를 요구한다. 실제 개선은 아직 확인되지 않았다. 이 실험 결과를 현재 기준망의 특성으로 섞지 않는다.

## 기존 증거에 따른 출발점

- 기준 5400초에서 E8 지속 저속은 1350초부터 종료까지 남고 E0까지 상류 전파한다. E8은 직접 진출10682와 그 직전 진입10639 사이의 136m 차로1 구간을 함께 검토해야 한다. 진입램프만 원인으로 가정하지 않는다.
- 66의 마지막 900초는 시작301 + 유입101 − 정상 link이동100 − 삭제31 = 종료271이다. 이 감소는 정상 회복 기준을 충족하지 않는다. 1124:1의 lane4 목적정보는 이미 1.2km 이상 앞에서 제공되므로 단순한 늦은 경로 결정만으로 설명하지 않는다.
- 기준 전체 lane-change 삭제486건, 미삽입 잔여1845대는 별도 스트레스 시험의 한계로 보존한다.
- 특정 램프행 희망 수요는 vehicle input과 연속 route 선택으로 계산한다. 관측 통과량, 접근도로 전체 재고 및 혼잡 중 목적지별 재고 비율을 희망 수요로 대체하지 않는다.

## 빠른 기준 실행 확인

`evaluation/runs/fast_nc_baseline_s13_v1`: 실제 5400초 완료, 시작부터 native 종료까지 약 384.8초. 기존 검증된 r02는 약 543.5초였다. 같은 조건의 반복 성능 통계가 아닌 이번 실행시간 비교다.

전체 FZP 26,693,633행 payload와 native LSA 30,845개 사건이 기존 기준과 exact다. 물리 readback 751행도 일치하고, 삭제486/미삽입1845가 재현됐다. 따라서 이후 후보에는 이 전수 동등성 검사를 반복하지 않는다. 기존 Ω·혼잡 분석도 그대로 재사용한다.

원래 fast v1 래퍼는 PowerShell process handle을 일찍 보존하지 않아 OS exit code가 null로 기록됐다. 원 receipt는 변경하지 않았다. `baseline_equivalence.json`에 별도 native 완주·자연종료·stderr 공백·전체 궤적/신호 일치 근거를 보존했다. 작은 cscript 종료0/7 재현으로 handle 보존 수정이 확인됐고 다음 후보부터 사용한다.

첫 후보는 `exit_a080.inpx` + `demand_sweep/a080/input_override.csv`다. input1098의 6개 구간 입력을 16/17배로 낮추고 1130:3 가중치만4→3.2로 변경한다. 다른 두 source-route 목적지 수요와 나머지198 input/interval 설정은 보존한다. route ID·경로·geometry·LCD·SIG는 변경하지 않는다. 첨두 직접진출 희망수요는2038.154→1630.523대/시다. 전후표는 `demand_sweep/a080/desired_demand.csv`이며 확률적 실현 차량수와 구분한다.

## 추가 사용자 허용: 전체 과포화 시 전체 수요 감소

사용자는 망 전반이 과포화라 판단되면 전체 수요 감소도 허용했다. 이에 따라 목적지별 감소 실험은 보존하고, 필요하면 원래 기준망·원래 route 비율에서 34개 입력/6개 구간의 최종 수요를 공통 배수로 줄이는 별도 조건을 비교한다. 이 조건은 비대상 목적지 수요도 동일 배수로 감소하므로 앞의 선택적 감소 조건과 명확히 구분한다. 실행 중인 직접 진출80% 조건의 종료 후 결과를 먼저 확인하고 다음 배수를 결정한다.

### 직접 진출80% 완료: 제어 시험 조건으로 미선정

5400초/exit0 완료, native 런 약364.8초, 종료 후 단일 궤적 처리 약96.5초. Ω TTT5384.498veh·h, TTD26488건, 종료재고4776, 미해결 내부소멸413, native 삭제480, 미삽입955(1098:264 /1099:545 /1105:146).

종료 E8=152대/11.432km/h, E0=204대/8.224km/h, E12=207대/7.271km/h다. 66은 기준과 같은 종료271대/정지233대이며 마지막900초 재고감소는 삭제31대에 의존한다. TTT 감소만으로 개선 조건으로 선택하지 않는다. 10681은 끝재고0이고, 첫 감소는 E8과 도시66의 과포화를 충분히 해소하지 못했다.

다음 조건은 원래 route 비율과 원래 기준망에서 전체 수요60%(`global060/prepared`)다. 이미 시행한 선택적 감소와 중복 곱하지 않는다. 회복 가능한 하한 쪽 조건을 찾은 뒤 혼잡이 지나치게 약하면 중간 배수로 올린다.
