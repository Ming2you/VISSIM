Use `trace_root_compression_v2.patch` (SHA256 `b332ec32914f3b7332f27765bc5d38839ad26b873bd01a9004393b5cef233fc9`) after the current trace pair has ended and root authorizes application. The running tracer, launcher, runtime and active databases were not modified. Git was not invoked. Root should perform the final apply check against its frozen checkout.

The earlier `trace_root_compression.patch` remains historical and is superseded. Revision2 adds only explicit conversion of an overflowing corrupted length to `ValueError`, plus its counterexample. The first revision's tests and synthetic timing JSON remain unchanged.

`Store.put` still creates the complete current canonical JSON bytes and hashes them with SHA256. A new root is stored as version prefix + eight-byte uncompressed length + zlib level1 bytes. A root already in the snapshot table is reused. There is no subtree hashing/SQL traversal for newly written roots and no mutable-object-ID cache. `Store.get` recognizes this format, checks decompression completion, exact size, absence of trailing streams and then the complete parsed-value SHA against the public key. Old DAG snapshots follow their existing reader and integrity checks. Public keys, row ordering, candidate values, operational snapshots, identity proofs and normalized comparison rules are unchanged.

Memory remains bounded by the current largest snapshot/serialization/compression buffers, SQLite's existing2 MiB page cache, and the existing1 MiB node cache; previous candidates remain disk-owned. This is not a new absolute maximum for an arbitrarily large single snapshot. Changing roots now duplicate compressed cfg/state content on disk. No full-history values are retained in Python. The old reader cannot read the new binary descriptors; the proposed reader handles both formats. Preserved old fixtures therefore remain readable, while newly written traces require the new reader.

No traffic model or live database was loaded. The production storage SHA was equal before and after.

These very short CPU measurements have coarse resolution; another actual trace was active. They demonstrate a storage-only tradeoff, not a reliable speedup estimate for the full trace. The observed threefold disk increase is specific to this fixture.

The current actual full trace has not established a storage bottleneck decomposition or completion under its3600-second timeout. This patch does not remove the Python `canonical()` traversal, typed-key sorting, large operational snapshots, or the caller `digest()` followed by `put()` serialization. Thus it may be insufficient for full-trace completion. The next authorized check should compare a bounded identical real local fixture under both transports before another full pair, retaining every candidate/score and both exact comparison hashes. No result or scope may be dropped to reduce trace cost.
