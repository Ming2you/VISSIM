VISSIM shared storage layout (2026-10-19)

1. Common, immutable data
   D:/VISSIM_shared/objects/sha256 and E:/VISSIM_shared/objects/sha256
   Identical contents share the same physical file on each volume. Historical
   experiment paths remain readable as read-only NTFS hardlinks. High-use small
   inputs use additional verified shards to stay below the NTFS link limit.
   Different versions of a network remain distinct by content hash.

2. Editable code and input preparation
   E:/VISSIM_workspaces/vsl349_causal_20261011 remains an independent editable
   source. Shared inputs must not be edited in place. The canonical runners
   create private writable INPX/SIG copies when an experiment must modify them.

3. Future packages
   Use tools/sdmpc31/runtime_package.py prepare with the actual source-relative
   --config (or protocol) and any necessary --include entries. This produces a
   pinned input manifest. Historical result archives and evidence.part files
   are not copied implicitly.
   Pass that manifest as -InputManifest to tools/sdmpc31/freeze_worktree.ps1,
   together with -Source, a unique -FrozenRoot, -SharedStoreRoot and -Python.
   Freezing without an explicit input manifest is refused. The canonical
   freeze manifest verifier remains mandatory.
   A prepared input manifest can be reused while its pins still match. Source
   or dependency changes require an updated selection. External references
   are pinned and remain external; they are not silently bundled as outputs.

4. Run results
   Use a separate, unique ResultsRoot and the established canonical preflight
   and runner. Do not resume an old queue merely to test this storage change.
   Storage verification does not qualify new native controller behavior.

5. Historical records and physical capacity
   Directory size totals count each hardlink path again. To measure reclaimed
   capacity, use drive free space, not the sum of folder sizes.
   Unique original results/FZPs, editable workspaces and small metadata remain.
   The migration plan and journal record every replacement and restoration.
   storage_layout_complete.json is the final completion record; its absence
   means the migration has not yet been closed and verified.
