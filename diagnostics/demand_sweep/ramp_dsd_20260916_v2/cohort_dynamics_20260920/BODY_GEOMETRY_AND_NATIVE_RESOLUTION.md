# 실제 차체 좌표와 VISSIM 계산 해상도 진단

2026-09-21, `1f378f3` 이후 로컬 후속. **RM/VSL 이득 예측 NOT_QUALIFIED, 목표 active.** 초당1단계 좌표 관측은 완료했으나, 초당10단계 재실행은 C: 공간 고갈로 실패했다. 실패 런의 닫힌1500.1초 prefix만 예비 분석했으며 본격 혼잡 구간 비교는 미완료다. 소유 프로세스는 모두 종료로 확인했다.

## 완료된 확인

기준 사용자 망은 그대로 두고 NC seed23에 차량 앞·뒤 X/Y 좌표와 가속도5개 열만 추가했다. 기존 runner의 fixed profile 경로이며 명령0개, 3000초, native 신호/설정 readback을 유지했다. `body_geometry_native_v1/none_s23_res1/run`은 완료했고 소유 native 프로세스도 종료했다. 864개 초기/최종 주소, native LDP150,000행·1,320,000표본 검사를 통과했다.

기존 원본20개 열은 **11,788,963행 전부 정확히 같다**. 비교 해시는 `8c604bb172fda689f6f003ea2618e45acb1087c843bf27e296717110ec03b660`이며 `reference_original20_prefix.json`과 `analysis_res1/result.json`에 보존했다. 기존164개 압축 관측 프레임도 일치한다.

설정 파일뿐 아니라 기존 완료 런과 새 런의 실제 readback에서 `SimRes=1`이다. [PTV2020 문서](https://www.cgi.ptvgroup.com/vision-help/VISSIM_2020_ENG/Content/9_SimulationundTest/Simulationsparameter_setzen.htm)는 이 값이 차량 위치 갱신 횟수/초이며 해상도 변경이 교통 결과도 바꾼다고 설명한다. 따라서 다른 해상도는 새로운 진단 조건으로만 비교하며 동일 궤적이나 개선된 정본으로 취급하지 않는다.

## 투영 겹침은 측방 위치만의 문제인가

## 실행 코드의 최소 수정

- 기존 `prepare_vehicle_lengths.py`에 명시적 `--body-resolution {1,10}` NC 관측 옵션을 추가했다. 해상도와 추가5개 출력 열 이외의 XML·신호 자산·수요·경로는 그대로인지 확인한다. 기존 CLI 기본 분기는 유지한다.
- 기존 `fast_fixed_profile.py`는 `native_resolution_probe`가 명시되고 명령이 전혀 없을 때만 저장된1/10해상도를 허용한다. 평소 제어 경로의SimRes1 제한은 유지한다. 기존NC/RM/VSL 세 프로파일의 event/initial/proof는 수정 전과 정확히 같다. 관련8개 검사는 PASS다.
- 첫10단계 실행에서 출력이0.1초였음을 발견했다. 설치된2020 `attribute.xlsx`의 Evaluation/VehRecResolution 설명은 **time steps 단위**다. 해당 런은1초 출력 계약 실패로 보존하고, receipt의 PID·생성 시각을 실제 프로세스와 대조한 두 소유 프로세스만 종료했다. 초기 이름/시각 비교 실패에서는 아무것도 종료하지 않았다. 최종 비교는 VISSIM200 이름과 UTC ticks를 사용했다.
- 기존 `fast_nc_runner.vbs`의 native-preserve/fixed 분기에서 출력 단계를 현재SimRes만큼 지정하고 한 번 readback을 남기도록 고쳤다. SimRes1의 설정값은 계속1이다. 별도 runner/adapter는 만들지 않았고 동역학·제어 명령 쓰기는 추가하지 않았다. VBScript문법 PASS다.
- 광범위한 기존15검사 중14개는 통과했다. `fast_nc_test.test_no_model_or_census_and_one_continuous`는 기존MPC 전용 함수의 차량 조회 문자열까지 금지하는 정적 검사 때문에 실패했으며 수정 전 소스로도 같은 실패를 확인했다. `preexisting_static_test_failure.txt`를 보존했고 이 검사를 성공으로 바꾸거나 MPC 관측을 삭제하지 않았다. 이번NC 경로에는 해당 함수 호출이 없다.

## 공간 확보와 재개 조건

C: 공간 고갈로 기본 셸 생성도 일시 실패했다. 다른 사용자 자료나 유효 native 원본은 삭제하지 않았다. 소스가 존재하는 재생성 가능한.pyc359개(약7.7MB), 인계 압축본과 해시가 같은 임시 복원본35개(약50.6MB)만 정리했다. 각각`cache_cleanup.json`, `restore_temp_cleanup.json`에 목록이 있다. 일부 임시 폴더는 일반 호스트 프로세스에서 권한이 없어 정리하지 못하다가 원래 sandbox 경로에서 검증·정리했다.

종료된 첫 실패 FZP의 NTFS 무손실 압축도 시도했다. 최종 명령은 성공했으나 압축률1:1로 추가 공간을 확보하지 못했다. SHA256 `6c10f72cb84cc766e76e49ce1b8fb6c641bd405765c96f7441ef6c63db276a17`은 전후 동일하다. 현재 남은 공간은 약35MB여서 native를 재시작하지 않았다. 사용자가 C: 약10GB 이상을 확보하거나 다른 보관 경로를 지정하는 질문을 보냈으며 답변은 아직 없다. 이 저장 공간 문제의 첫 goal 턴이며 blocked 상태로 바꾸지 않았다.

기존 `fast_nc_run.ps1`에 선택적 `-MinimumFreeGiB` 검사를 추가했다. 다음 진단은10으로 실행하며, 시작 전 부족하면 native/출력 폴더 생성 전에 거부한다. 이 옵션을 켠 런은128MiB 아래에서 기존 소유PID/시작시각 종료 절차로 부분 기록을 보존한다. 기본0에서는 기존동작을 유지한다. 문법 검사와 공간부족 시작 거부를 실제 runner 호출로 확인했다. 실행 중128MiB 중단 경로는 코드 검토만 했고 별도 native 실험은 하지 않았다.

공간을 확인한 후 새 출력 폴더의3000초 런을 시작한다. 과거 실패 폴더를 덮어쓰거나 존재하지 않는 완료 결과를 재사용하지 않는다. 새 런 경로를 분석기의명시적 run-name에 추가할 때 기존 prefix producer 소스를 보존한다. 런 중 대용량 분석은 수행하지 않는다.

먼저 해상도별 기록 간격·누락·차로별 혼잡 노출·겹침 빈도와 속도/차량 수를 비교한다. 고해상도에서 겹침이 줄더라도 혼잡 노출이 줄었기 때문일 수 있으므로 단순 건수만으로 수치 해상도 원인을 확정하지 않는다. 바뀐 해상도의 결과를 기존 모델의 개선이나 RM/VSL 이득으로 보고하지 않는다. 유의미한 차이가 확인되면 이후 보정·제어 반응 짝 비교에 사용할 해상도를 명시적으로 결정해야 한다. 차이가 작으면 좌표 단서를 일반화하지 말고 기존 가감속/방출 장부로 돌아간다.

정본 core4파일·사용자 기준망·수요·모델 기본 설정은 이번에도 바꾸지 않았다. 전체 Ω/full GNE와 미사용 검증은 미완료다. 이번 후속은 아직 푸시하지 않았다.
