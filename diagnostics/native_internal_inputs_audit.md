Before this repair, only input 1091 had an explicit future-generation contract (160 veh/h); the other nine accounted for **1960 veh/h of desired demand**. The measured internal-demand aggregate and initial observed inventory did not inject those vehicles into the prediction. Desired volume is not the same as vehicles actually admitted by VISSIM or by a finite model receiver.

## Why the old aggregate did not compensate for missing inputs

The actual run used `urban_input_gate_map_ver2_20260907.csv`, not an assumed filename from old documentation. Each of these ten rows has status `internal` and an empty gate. The relevant old legs4b1091 row agrees; the actual run's Ver2 pin and manifest are the authority. `AddUrbanGateDemand` in the canonical VBS adds these inputs to `urban_internal_volume_vph`, whereas only mapped inputs become `urban_volume_vph_by_gate`. The adapter's old profiled urban demand used the latter table. All candidate origin keys associated with these ten sources had zero external forecast in the audited state. Their observed initial stock, far measurements and zero-valued external gates are not substitute future-generation contracts.

Input1101/source69 is separate: gate status `shared_stem_unmapped`, desired1333 veh/h at1350 s, and its validated shared-approach generator already owns admission. It is not part of the2120 internal bucket. The four observed on-ramp forecast values aggregate traffic reaching ramps; they do not identify or replace individual missing native source admissions and must not be subtracted as if they did.

The runner uses the original INPX schedule multiplied by run demand scale and pinned role/no overrides. In the audited run, scale1 and urban-input multiplier1 leave the native urban schedules unchanged. The six common boundaries are0/900/1800/2700/3600/4500 s. Integrated over5400 s, total desired internal demand is2570.5 vehicles; the original nine unsupported inputs contribute2376.5 desired vehicles. Neither number asserts actual admission. The native helper validates run/network/profile/gate/role hashes and the current internal aggregate before using schedules.

The opt-in `prediction.native_input_schedule` additionally publishes all34 validated input schedules as plain runtime data for the separate external-demand forecast helper. Only external mapped gates/mainline forecasts use that field. Native internal and shared generators keep their own admission schedules; observed ramp estimates remain separate.

## Route and calibration limits

The common-approach validator proves ordered physical paths, exhaustive permitted pre-stopline branches, source isolation, canonical receiver identity and the first selected signal. It rejects source21's tempting downstream alias because it would bypass SC108. Nonselected native heads are recorded as a limitation instead of being relabeled as MPC authority. The existing aggregate approach travel model does not resolve those native clocks, and existing downstream turn beta is not automatically equal to native relFlow.

The1092/1093 calibration is `native_1092_1093_branch_calibration.json/.csv`. It records all147 observed source cohorts, alternative physical branches, zero unresolved/censored cases and the1 s skipped-connector distinction. Its full seed13 data are an offline calibration prior; using it for the same seed's earlier predictions is in-sample exploration. A separately frozen seed14 run is required for holdout validation. Runtime must never read the current controlled run's future trajectories.

The implemented repairs use existing finite approaches and narrowly scoped route/signal helpers. They do not add initial-stock constants, rescale observed inventory, create fake boundary entries, disable unresolved-support guards, alter player territory or duplicate the adapter. Actual VISSIM comparison and held-out prediction validation remain distinct from these conservation and runtime checks.
