# 시작 문제와 네트워크 변경의 실제 검증

**시작 전 COM 수요 설정에서 발생하던 실패를 수선했고, 원래 망·거리 확대·상류 경로 분할 세 망이 모두 1,050초를 완주했다. 교통 성능은 별개다. 이번 두 네트워크 변경을 개선된 정본으로 채택할 근거는 아직 없다.**

사용자의 추가 요청에 따라 1,050초 결과만으로 효과를 판정하지 않고, 동일 세 망의 **무제어 5,400초** 비교를 우선한다. 17:29에 `no_control_network_arms/r01`의 원래 망을 시작했다. 신호는 native 고정 주기, VSL120·meter GREEN의 기존 무제어 명령, seed13·동일 수요다. 원래 망의 전체 궤적 재현을 통과한 뒤 다음 망을 순차 실행한다. 아래의 짧은 제어 실험은 국소 현상 근거로 보존하며, SC1004 타이밍 반사실 실험은 전체 무제어 혼잡 분석 이후로 미룬다.

## 시작되지 않았던 이유와 수정

실패한 r03의 마지막 호출은 첫 RunSingleStep이 아니라 `ApplyDemandMultipliers`의 Volume setter였다. input1097의1-5 구간에 target0을 쓰려다 실패했는데, 원본 INPX의 값은112 veh/h이고 적용 배율은1이다. 기존 `SafeAtt → ToDbl` 경로는 읽기 실패를0으로 바꿀 수 있었다. 작은 VBScript 재현으로 이 경로를 확인했다. 다만 해당 실제 실패에서 최초 read 오류 번호는 기존 로그에 남지 않아, 그 호출이 실패한 내부 COM 원인까지 확정할 수는 없다.

canonical VBS에서 기존 QuickMode/SuspendUpdateGUI를 LoadNet 직후로 옮겼다. 수요 읽기의 오류·빈 값·비수치 값을 즉시 거부하고, setter 오류 번호와 설명을 호출 직후 보존한다. 모든 정상 수요 write·readback·배율·적용 순서는 유지했다. 같은 값의 setter를 생략하는 최적화는 하지 않았다. 구간별 write와 각 시작 단계의 시간을 추가했다. 원래 VBS 바이트와 실패 런은 별도로 보존했다.

fake 검사6개/child cscript10개가 모두 종료했고, 실제 기준 런에서는 원래 beta300v3의 **전체1,990,205행 FZP ordered payload, 제어 명령, native signal/ramp/VSL readback이 정확히 일치했다.** 따라서 이번 기준 런에서 시작 수선이 교통을 바꾸지 않은 것은 확인됐다. 세 번의 새 완주는 시작 문제의 재발 방지를 지지하지만, 모든 향후 COM 환경에서의 무실패 보증은 아니다.

모두 startup/stall300초, 단일 라이선스 순차 실행, 소유 native 프로세스 잔존0이었다. [실행 증거 묶음](startup_gui_three_arm_comparison_v1/manifest.json)은 세 원래 receipt와 현재 입력 SHA를 연결한다. 옛 실패 manifest를 통과 상태로 덮어쓰지 않았다.

## 거리 확대가 해결하지 못한 차로 정체

10641은126의1·2차로에서71의2·3차로로 들어온다. 반면10635는71의4·5차로를 사용하며, 진입점부터 분기까지는77.6908m다. 10635는 도시47 방향 connector이고 on-ramp가 아니다.

900–1050에71→10635 관측 출발은15→18대로,71 전체 connector 출발은48→52대로 늘었다. 그러나1050초71의 재고18대·정지15대는 같고, 핵심 차량4725는 두 망에서 독립적으로 같은 실패를 재현했다. 929–965초 SG2 녹색37개 표본 동안3차로 POS73.39에 정지했고, 차로 변경 없이973초에45초 차로변경 대기 후 제거됐다. 제거는 정상 방출이나 TTD에 포함하지 않았다.

옆4·5차로도 정지열이었다. SG5는969초에 녹색이 됐고 선두의 첫 움직임 표본은971초였다. 그 뒤에야 열이 풀리기 시작했으므로4725 제거 전 여유가 짧았다. 뒤4387은 제거 다음974초 움직였지만 다시 SG2 적색을 만나1047–1048에야10634로 통과했다. 같은 기간 다른1·2차로는 방출했으므로, 전체 접근로 용량을0으로 취급하는 설명도 부정확하다.

이는 **목적 차로의 정지열과 현시 순서·시점**을 함께 보아야 한다는 증거다. 초기922–925의 차로변경 가능성, 차량 길이를 뺀 실제 gap, VISSIM의 개별 차로변경 거절 이유는 현재 표본으로 확정하지 않았다. [차량·차로별 시간 분석](lane_opportunity_4725/report.md)에 수지 검증과 원자료 범위를 기록했다. 다음 실험은 SC1004 offset+18.75초와 p3에서p4로18초 녹색 이전을 각각 분리하는 것이다. 효과는 아직 검증 전이다.

## 상류 경로는 적용됐지만 효과는 미확정

상류 실험 망의 하류 decision1135와 소속 경로는 실제로 삭제됐다. 1123·1124·1125의 새4·5·6 경로9개는 모두 실제 current-route 표본에서 관측됐다. 750/900/1050의 확장 경로242개 관측 중190개는 차량이 아직 부모 접근로52/66/46 위에 있을 때다. 같은 차량이 여러 시점에 포함되므로190대의 독립 차량으로 해석하지 않는다. 하류1135의 current-route 표본은0이다.

따라서 설정만 저장되고 전혀 적용되지 않은 상태는 아니다. 그러나 기존 Combine/LookAhead가 미리 결정한 미래 경로를 current-route 속성이 모두 노출하는 것은 검증하지 않았다. 새 수동 분할이 모든 차량에 추가 선행 정보를 주었다고 단정하지 않는다. [실제 경로 표본 감사](startup_gui_upstream_route_activation_v1.json)는 선택확률·전체OD 보존의 증거와 구분한다.

## Ω 전체 결과

Ω는 원래 고속도로+도시 protected network의635개 물리 링크다. 살아서 외부 링크로 이동한 유출과 검증된 망 말단 이탈을 포함하고, 내부 이동은 제외했다. 끝나지 않은 차량과 내부 원인불명 소멸은 TTD에 넣지 않았다. TTD는 경계 유출 사건 수이며 반복 유출은 별도 기록한다.

전체0–1050 TTT도375.45639→376.34667/376.87486으로 늘었다. 전체TD는3421→3425/3414다. 거리 확대의420 정지차량16→3 감소나 상류 분할의16→2 감소만으로 망 전체 개선을 주장할 수 없다. 두 변경은0초부터 적용되어900초 상태부터 다르며, 한 seed의 짧은 실험으로 분산이나 장기 개선을 판단하지 않는다.

[Ω 측정·경계 검증](startup_gui_three_arm_area_v1/assessment.md)에서1050개1초 프레임, tail0, 매초·모든창 차량 수지0, 링크별 TTT 합과 방향별 유출 합을 확인했다. [공간 비교](startup_gui_three_arm_spatial_v1/comparison.json)는750–900/900–1050의 차로, 현시, 도착·방출을 구분한다.

## 남은 작업

시작 수선과 별개로 계산 최적화의 전체 후보 추적 비교가 진행 중이다. 정상 실행에서 확보한15–19% 단축을 상세 추적의 경과시간과 섞지 않는다. 전 레버 follower game은 실제 실행값·공유 수용 유량·국소 비용과 가격의 일치를 검토한 뒤 통합해야 하며 아직 완료하지 않았다. SC1004 신호 반사실 실험, 장기 폐루프·β 비교와 최종 정본 리팩터링도 남아 있다.
