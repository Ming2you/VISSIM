# 램프 보정값 연결 누락 수정과 남은 도착 오차

완료된 expanded036 seed29의2250초·3600초 기록으로 검사했다. 현재 CTG 실행은 조회·변경하지 않았다. 새 VISSIM·FZP 스캔·계수 탐색·push는 없다. 목표는 ACTIVE/NOT_QUALIFIED다.

**선언된 램프 이동속도 보정값이 실제 버퍼로 전달되지 않는 결함을 수정했다. 그러나 이것만으로 큰 합류 오차나 작은 RM 반응은 해결되지 않았다.**

## 실제 반응 검증

기존 native MER 청크에서10484 입구와 신호등 통과를 차량 번호로 연결했다.2250초 시작150초의 진입27대,3600초의23대 모두 추가150초 안에 head 통과를 확인했다. 이동시간 중앙값은 각각33.92초/32.23초였다. 이 시간에는 대기가 포함될 수 있어 자유류 속도 보정 표본으로 취급하지 않는다. 미래 기록은 사후 분석에만 사용했고 예측에 넣지 않았다.

1m 입구 검지 위치부터377.11m 신호등까지의 설정상 이동시간은27.76→32.27초가 된다. 신호 후 시간은12.16→8.73초로 줄지만 실제 합류는 여전히 수용 제약에 제한된다. 이를 회복 정확도 개선으로 자동 판정하지 않는다.

## 더 큰 도착 오차의 단서

2250–2400초29번 도로의 직진 head 두 개(960158·960159)에서31대가 통과했지만, 모델의 `SC1001_E_SC1002_to_W_RAMP` 방출은 **2.5417대**다. 두 검지기는10119를 거쳐31번 도로로 연결된다.40번 좌회전은 실제13대/모델11.7333대로 차이가 더 작다.

29번 차량 전부가10484행이라는 뜻은 아니다. 실제10484 도착 중 앞선29번 head 통과와 차량 번호가 연결된 차량이 있고, 후반 도착 중 상당수는2250초 당시329번 등 더 상류에 있었다. 다음은 **SC1002→SC1001의 신호 방출·이동시간·목적지 queue 초기화** 중 어느 단계가 이 차이를 만드는지 확인한다. 그 전에 합류 감속 계수만 추가 조정하지 않는다.

## 기각한 가설·실패·검증 범위

- 초기에 공유 저장고 합계를 보고10483 차량이10484로 재선택된다고 설명했지만 **이번 실효 모델에 대한 잘못된 해석이었다.** 경로 보존과 목적지별 이동 기능은 이미 켜져 있었고 direct_exit 경로 상태도 존재한다.10483의124→10775→125 출구행 태그가 유지된다. 새 예측 전에 기각했으며 `../routing_correction/REJECTED.md`에 정정했다.
- 예산4회 중2250초 유지·g8,3600초 유지의3개 결과가 저장됐다.2250초 g8/6/4 계산은 trace 저장 시 Windows 경로 길이로 실패했다. 결과 없는 후보는 통과로 세지 않았고 반복 계산하지 않았다. VISSIM 실패가 아니다. 다음3600초부터 짧은 라벨을 썼다.
- 기존 램프 검사7개 통과,8번째 오래된 기하 smoke 검사는 해당 폴더의 `port_profile.json` 부재로 실행 오류였다.8개 전체 통과라고 보고하지 않는다. 실제 선택망 초기화와 저장된 예측에서는8개 램프 보존·명령 변경·31셀 상태 검사를 통과했다.
- N_P/N_UF·SDMPC 선택·native 제어 이득은 이번에 검증하지 않았다. 보정값 연결 수정 완료와 제어 이득 예측 보정 완료를 구분한다.

## 증거

`before_2250_audit.json`/`after_2250_audit.json`은 실제 버퍼 불일치/일치, `verification.json`은 저장 예측·기존 기준 재사용·보존·명령 검사, `native_timing.json`은 차량별 통과 시각과 SHA256이다. `protocol.json`에 예산·세션·실패·STOP/설정/다른 코드 해시를 보존했다. 수정 전후 소스는 `lane_plant_runtime_before.txt`/`lane_plant_runtime_after.txt`이며 AST 비교에서 `initialize` 한 함수만 바뀌었다.

재현은 `../check_speed_binding.py`, `../native_timing.py`, `../summarize_binding.py`가 담당한다. 기존 초기화와 probe를 호출하거나 저장 결과를 검사하는 진단이며 별도 VISSIM runner가 아니다.
