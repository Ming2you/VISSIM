작업 방향을 보완하고 싶어. 앞으로는 모든 control lever를 동일한 follower game의 전략변수로 포함하고, 그 최종 제어에 대해 GNE 근사와 실행 정합성을 검증하는 방향으로 진행해줘.

기존의 Stackelberg leader + marginal-price + distributed follower 구조는 유지하고 싶어. 다만 현재 구현이 그 구조를 실제로 충실하게 구현하는지는 독립적으로 판단해줘. 클래스 이름이나 nash_converged 플래그만으로 구조와 수렴이 보장된다고 생각하지 말아줘.

아래 내용은 사이드 대화에서 코드와 완료된 런을 읽고 확인한 사항이야. 이후 메인에서 수정된 부분이 있으면 현재 코드와 대조하고, 이미 해결된 작업은 반복하지 마.

1. 현재 확인된 문제

최근 beta300 1050초 검증 런에서 최종 채택된 PFO 후보는 900초와 1050초 모두 Jacobi 1회 후 종료했어. 결합변수 정규화 잔차는 각각 약 0.01998, 0.03553이고 종료 기준은 0.05였어.

이것은 각 agent의 추가 개선 가능성을 확인한 Nash gap이 아니고, nash_residual_objective=0도 실제 목적함수 잔차를 계산한 값이 아니라 고정 반환값이었어.

Metering은 Jacobi 안에 들어가 있지만, offset은 반복 후 별도 탐색하고, 현시별 green 재배분도 phase refinement로 뒤에서 처리하는 설정이었어. 최종 green은 각각 59개, 29개 값이 추가 변경됐는데, 변경된 최종 제어에 대한 합의 반복은 다시 수행하지 않았어.

이 경우 앞서 계산한 follower의 최선응답이 최종 실행 제어에서도 유효하다고 보기 어려워. 최근 수정을 통해 최종 제어를 목적함수로 다시 평가하게 된 것은 필요하지만, 그것만으로 GNE 수렴이 보장되는 것은 아니야.

2. 목표로 하는 follower 구조

도시부 교차로 agent는 전체 현시 green 벡터와 offset을 함께 전략변수로 가져야 해.

고속도로 agent는 자신이 담당하는 VSL 구간들의 속도와 소속 ramp metering을 함께 전략변수로 가져야 해. 현재 VSL 구간별 제어 권한과 물리적 소유 관계도 확인해서, 서로 다른 agent가 같은 실행 레버를 중복 소유하지 않게 해줘.

모든 레버의 변경이 다른 agent의 유입, 도착 시각, 수용 공간, 방류 가능량에 반영되고, 그 변화에 다른 agent가 다시 반응하는 반복 구조를 만들어줘.

모든 조합을 전수 탐색하라는 뜻은 아니야. Agent 내부에서 교대 탐색이나 좌표 탐색을 사용할 수 있지만, 앞서 고른 레버를 다시 검토해야 하고, green–offset이나 VSL–metering을 함께 바꿔야 개선되는 경우도 확인해야 해. 개별 좌표가 멈췄다는 이유만으로 agent의 최선응답을 찾았다고 간주하지 마.

단순히 phase_price.in_gne 스위치를 켜는 것으로 끝내지 말고, 실제 실행 경로 전체에서 이 구조가 성립하는지 확인해줘.

3. Leader·가격·공유 제약의 관계

Leader의 목표 후보, 외부효과 marginal price, 공유 제약을 처리하는 쌍대변수 λ의 역할과 갱신 시점을 명확히 구분해줘.

주어진 leader 후보와 외부효과 가격 아래에서 follower game을 풀고, 최종 follower 응답을 동일한 영역 목적함수로 평가해 leader 후보를 비교하는 구조를 유지해줘. 가격을 고정하는 범위와 재계산 조건도 명시해줘.

공유 용량과 저장공간은 여러 agent가 각각 전부 사용할 수 있는 독립 자원처럼 처리하면 안 돼. 최종 결합 제어의 실행 가능성을 확인해야 해. Soft penalty를 넣었다는 이유만으로 hard constraint가 충족됐다고 간주하지 마.

PFO를 유지한다면 같은 물리 모델과 평가 기준을 적용하고, 최종 선택이 leader 후보인지 PFO인지 분명히 기록해줘. PFO 선택을 Stackelberg 상위 조정의 성능 향상 증거로 보고하지 마.

4. 목적함수와 TTD 정의

Ω는 제어 대상 고속도로 + 도시부 protected network의 합집합이야.

TTT는 Ω 내부 차량 체류시간만 계산하고, TTD는 Ω 밖으로 나가는 차량 수야. 차량이 VISSIM에서 사라지지 않고 non-control area로 이동한 경우도 포함해. Ω 내부의 고속도로↔도시부 이동은 TTD가 아니야.

TTT를 차량·시간 단위로 쓸 때 JΩ = TTTΩ − (β/3600) × TTDΩ를 사용하고, 가격 계산에도 동일한 TTD 효과가 들어가야 해. 국소 비용과 가격에서 효과가 중복 계산되지 않는지도 검토해줘.

β는 아직 최종 확정하지 않았어. 기존 후보별 실제 결과를 보고 결정할 거야. 알고리즘 효과와 β 효과가 뒤섞이지 않게 비교해줘.

그리고 TTT만 써도 괜찮아. TTD가 TTT가 못잡는걸 보완해줄 수 있나 궁금했던 거였고, TTT + cost-to-go(far price)로 해결될 수 있는 문제라면 굳이 TTD를 꼭 넣지 않아도 좋아.

5. 수렴·실행 검증

최종 제어에서 다음을 구분해 기록해줘.

- 레버 및 결합변수의 변화량
- 공유 제약 위반량
- 각 agent가 실행 가능한 다른 전략으로 얻을 수 있는 추가 비용 감소
- 반복 상한이나 계산 시간 예산 때문에 종료했는지
- 실제 채택된 후보와 그 후보의 검증 결과

후보 일부만 탐색했다면 “검사한 후보 범위에서의 개선 잔차”라고 표시해줘. 그것을 엄밀한 ε-GNE 보증으로 부풀리지 마. 비볼록·이산 제어 때문에 보장할 수 없는 부분도 명확히 구분해줘.

Offset 정규화, VSL 양자화, metering 실행 변환, signal 제약 처리를 포함한 실제 전달값을 기준으로 검증해야 해. 검증 후 제어값을 바꾸는 단계가 남아 있다면 재평가·재검증하거나, 실행 가능한 후보를 처음부터 탐색하도록 정리해줘.

6. 직접 수정하고 VISSIM으로 검증

진단 → 코드 수정 → VISSIM run → 결과 분석 → 다음 진단의 흐름으로 진행해줘.

우선 동일한 기록 상태에서 기존 방식과 수정 방식을 비교해 구현 오류와 계산 특성을 확인하고, 이후 동일 seed·수요·초기 조건의 실제 폐루프 비교를 해줘. 짧은 smoke run과 전체 평가 run을 구분해서 보고해줘.

TTT·TTD뿐 아니라 정체 발생 위치와 시점, queue 전파, spillback, 램프와 본선의 상충, 신호별 실제 방류, green·offset과 platoon 도착의 관계를 분석해줘. 각 레버가 왜 그렇게 움직였고, 그 결과 다른 agent가 어떻게 반응했는지 확인해서 다음 수정에 활용해줘.

모형이 실제 교통을 잘못 예측하는 문제와 게임을 제대로 풀지 못하는 문제를 구분해줘. GNE 내부로 레버를 옮겼다는 사실만으로 교통 개선을 가정하지 마.

7. 계산 성능 개선을 최우선으로 먼저 진행

번호는 7번이지만, 실제 작업 순서에서는 이 항목을 최우선으로 진행해줘. Decision 계산이 빨라지면 이후 GNE 수정, 가중치 비교, 반복 진단과 VISSIM 검증에 드는 시간이 모두 줄어들기 때문이야.

이미 진행 중인 유효한 런과 결과는 보존하면서, 다음 대규모 반복 실험에 들어가기 전에 성능 병목을 먼저 확인하고 개선해줘.

단, 목적함수·물리 모델·탐색 범위·수렴 기준을 약화해서 빨라지는 것은 원하지 않아. 첫 단계 목표는 “동일한 문제를 풀고 동일한 결과를 내면서 계산 낭비를 제거하는 것”이야.

곧 모든 레버를 GNE 안으로 통합할 것이므로, 신호 실행 계산, 물리 rollout, 국소 후보 평가, 데이터 복사, worker 관리처럼 새 구조에서도 재사용할 수 있는 부분을 우선해줘. 폐기할 기존 후처리 구조만 정교하게 최적화하는 데 시간을 과도하게 쓰지는 마.

7-1. 정확한 성능 계측부터

최근 실제 decision은 약181초였지만, 지금 기록만으로 각 단계의 소요 시간을 완전히 분해할 수는 없어.

최종 선택된 follower의 solve 시간 약12~15초는 후보 한 개의 시간이지 전체 GNE·follower 평가 시간이 아니야. 나머지를 전부 가격 계산 시간으로 계산하면 안 돼.

또 wu_price_rollout_count=43은 전체 가격 rollout 횟수가 아니었어. 현시 가격의63개 후보+기준점1개와 일부 worker 내부 계산이 별도로 집계돼 있어.

다음을 부모·worker 모두 포함해 구분해서 측정해줘.

- 상태·입력 읽기, 검증, 모델 구성
- 각 레버의 가격 계산과 현시 가격 계산
- Worker 생성·초기화·직렬화·전송·대기
- Leader 예비 평가, 상세 평가, PFO 평가
- 모든 후보의 follower 반복 및 agent별 국소 평가
- 최종 실행값 변환, 예측, 검증, 출력
- 동일 계산의 재평가 횟수, 캐시 적중·무효화 횟수

전체 wall time, worker CPU time, 서로 겹치는 병렬 시간을 구분해줘. 병렬 작업 시간을 단순 합산해 전체 wall time으로 보고하지 마.

먼저 실제 병목 순위를 확인하고, 근거가 가장 강한 부분부터 수정해줘. 아래 아이디어의 순서는 사전 검토에 따른 제안이며 실제 측정 결과에 따라 조정해도 돼.

7-2. 우선 검토할 개선 방향

A. 신호 실행 계산 사전 계산·재사용

현재 phase_fraction 경로는 movement별 호출에서 같은 green 벡터 검증, offset 계산, 초별 녹색 여부 계산을 반복하고 있어. 신호창 배치 캐시는 있지만 전체 계산을 재사용하지는 않아.

동일한 신호 프로그램·green·offset·절대시각·시간 간격에 대해서 실행 스케줄과 방류 비율을 한 번 계산해 재사용하는 방법을 검토해줘.

후보가 변경되면 필요한 부분만 다시 계산하되, VISSIM과 맞춰 놓은 소수점, 주기, 경계 시각, FMod, amber/all-red 처리까지 그대로 보존해야 해. 검증 자체를 삭제해서 빨라지는 방식은 피하고, 검증된 불변 데이터를 안전하게 재사용해줘.

B. 동일한 국소 후보·rollout 재평가 제거

현시 교환, green–offset, VSL–metering 탐색에서 같은 후보를 다시 방문하면 같은 비용을 반복 계산하지 않도록 해줘.

캐시에는 실제 계산에 영향을 주는 상태, 차량 재고·도착 대기 상태, 수요, 결합정보, 가격·λ, 실행 제어, 물리 모델과 예측 설정이 반영돼야 해. 국소 물리 비용과 가격을 합친 점수를 구분하면 가격만 바뀔 때 재사용할 수 있는 부분도 검토해줘.

기존 _phase_ctx_cache는 재고와 가변 내부 유량 상태가 키에서 빠져 있어 정확성을 위해 초기화하는 부분이 있어. 이를 무작정 다시 켜면 안 돼.

우선 동일한 동결 문맥 안에서만 유효한 작은 캐시부터 도입하고, 후보·GNE 반복·decision·seed·config 경계를 넘는 재사용은 의존성을 확인한 뒤 확장해줘. 메모리 사용량과 잘못된 캐시 재사용도 검증해줘.

C. 가격 계산 프로세스 풀 재사용

가격 계산은 이미10개 worker로 병렬화되어 있지만, 여러 가격 채널에서 풀을 따로 생성·종료하고 있어.

우선 한 decision 안에서 풀을 재사용해 초기화와 전송 비용을 줄일 수 있는지 확인해줘. Worker가 이전 작업의 상태·가격·런타임 패치를 잘못 유지하지 않도록 문맥 교체와 격리를 명확하게 해줘.

Worker 수를 늘리는 것이 실제로 유리한지도 측정해줘. 기존 주석의 성능 수치는 참고만 하고, 현재 코드에서 재검증해줘.

D. 독립 평가 병렬화

현재 직렬인 leader 후보 평가와, 동일한 스냅샷을 보는 Jacobi agent 평가의 병렬화 가능성을 검토해줘.

단순히 parallel 설정만 바꾸지 말고, 후보 간 가변 상태·λ·캐시·최선값·조기 종료 의존성을 먼저 확인해줘. 기존에 재사용하던 계산을 worker마다 다시 수행하면 오히려 느려질 수 있어.

완료 순서 때문에 tie-break나 선택 결과가 달라지지 않도록 해줘. Leader 병렬화와 내부 가격 병렬화가 중첩돼 CPU·메모리를 과도하게 경쟁하지 않게 해줘.

7-3. 추가로 찾아볼 +α

위 네 가지에 한정하지 말고 프로파일을 보고 추가 개선점을 찾아줘. 특히 다음을 검토해볼 수 있어.

- 반복문 안에서 변하지 않는 네트워크 매핑·상수·신호 구조의 사전 계산
- TrafficState 및 차량 흐름 ledger의 불필요한 중복 deep copy 제거
- 동일한 최종 실행 제어로 귀결되는 후보의 평가 공유
- 같은 상태·제어·예측 설정에서 얻은 TTT와 TTD 성분을 분리 저장해 β별 재채점에 활용
- 동일한 rollout의 중복 호출이나 불필요한 중간 상태 보관 제거
- 수학적으로 유효한 하한을 사용할 수 있는 후보 탐색의 안전한 가지치기

복사를 줄일 때는 후보 간 상태 오염을 막아야 하고, 진단 자료나 검증을 무작정 없애면 안 돼.

특히 J=TTT−β·TTD는 음수가 될 수 있고 미래 TTD 보상도 있으므로, 기존 TTT 부분합 기준 조기 종료를 그대로 되살리면 안 돼. 안전한 하한을 증명·검증할 수 있을 때만 적용해줘. 가격 유한차분에 필요한 평가값을 탐색용 가지치기로 잘라서 가격을 왜곡해서도 안 돼.

β별 최적 제어가 같다는 뜻도 아니야. 입력과 제어가 완전히 같은 물리 평가만 공유하고, β에 따라 달라지는 탐색은 유지해야 해.

7-4. 결과 보존의 검증 기준

수정 전 기준 코드·설정·입력을 고정하고, 동일 기록 상태에서 수정 전후를 비교해줘.

비교 대상은 최종 TTT·TTD 총량만이 아니야.

- 가격값과 목적함수 성분
- 평가한 후보와 후보별 점수
- 선택된 leader/PFO 후보
- 최종 green·offset·VSL·metering 실행 명령
- 공유 제약 위반과 수렴 관련 잔차
- 필요한 다음 decision의 내부 상태

우선 비트 동일 결과를 목표로 해줘. 부동소수점 계산 순서 변경으로 차이가 생기면 원인과 범위를 명시하고, 선택 경계와 실행 명령에 미치는 영향을 확인해줘. 수치가 조금 비슷하다는 이유만으로 동일하다고 선언하지 마.

초기, 정체 발생, 심한 혼잡, 해소 구간 등 대표 상태에서 검증하고, 필요한 실제 폐루프 VISSIM 비교까지 진행해줘.

프로파일링을 켠 실행과 일반 실행의 속도를 섞어 비교하지 말고, 같은 자원 조건의 일반 실행으로 단축 효과를 확인해줘. 평균뿐 아니라 개별 시간, 변동성, 느린 경우도 보고해줘.

7-5. 알고리즘 변경과 성능 최적화를 분리

다음은 결과를 유지하는 계산 최적화와 별도로 취급해줘.

- 후보 수나 예측 지평 축소
- GNE 반복 수 축소 또는 종료 기준 완화
- 가격 갱신 생략이나 근사 가격 사용
- 비볼록 탐색의 초기값·탐색 순서 변경
- 일부 control lever를 다시 GNE 밖으로 이동

Warm start도 기존 탐색 결과가 달라질 수 있다면 별도 알고리즘 변경으로 평가해줘.

모든 레버를 GNE 안으로 넣는 작업 자체는 필요한 구조 수정이므로 결과가 달라질 수 있어. 성능 최적화의 동일성 검증과 이 구조 변경의 교통 성능 검증을 섞지 마.

7-6. 목표와 다음 작업 연결

현재181초를150초 아래로 내리려면 약31초,17%를 줄여야 해. 다만 앞으로 GNE가 충실해지면 계산량이 증가할 수 있으니,150초를 간신히 통과하는 것보다 반복 실험과 추가 검증을 수행할 여유를 확보하는 것을 목표로 해줘.

근거 없이 단축률을 약속하거나, 특정 목표를 맞추려고 계산을 생략하지는 마.

각 개선에 대해 “어떤 중복 계산을 줄였는지, 얼마나 빨라졌는지, 어떤 동일성 검증을 통과했는지, 남은 병목은 무엇인지”를 정리해줘. 측정 결과 효과가 없으면 과감히 제외해줘.

이 성능 개선을 가장 중요한 선행 작업으로 진행하고, 검증된 개선을 확보한 뒤 모든 레버의 GNE 통합과 나머지 진단·수정·VISSIM 반복 실험을 이어가줘. 사전 분석이나 계획 제시에 그치지 말고, 직접 수정하고 검증 가능한 개선을 만들어줘.
