# SDMPC 유량 계산·차량 이동 갱신 최적화

판정은 **NOT_SELECTED_FOR_SPEED: 전체 결정의 추가 시간 단축 없음**이다.
최종 후보는 **램프·본선 유량 질의에서 반복하는 제어 객체 복사를 줄이는 변경**이다.
실험 키는 `adapter.sdmpc_flow_update_cache` 하나이며 `sdmpc_prediction_cache`와
함께 개별 예측 범위 안에서만 활성화한다. 기본값은 OFF다.
이전 공간 분리 실험의 `spatial_receiving`은 켜지 않았다.

## 최종 후보의 범위

`lane_ramp_runtime.advance`는 매초 본선 방향별로 제어 객체를 깊은 복사한 뒤
램프 명령만 바꾸고 `compute_ramp_release_flows`를 호출했다.
`lane_freeway_runtime.advance`의 서측 본선도 같은 복사를 매초 반복했다.
이 함수는 VSL과 램프 입력을 읽기만 하고 제어 객체를 수정하거나 보관하지 않는다.

새 `ramp_query_control`은 객체를 얕게 복사하고, 실제 수정하는 `ramp_metering`
사전만 별도로 복사한다. 이 좁은 질의에서 읽기만 하는 나머지 제어 항목은
공유한다. 제어 계산·상태 이동·FIFO·수용 한계·이동 지연·검사는 그대로다.
키가 없거나 예측 범위 밖이면 기존 깊은 복사를 수행한다.

vendor와 유일한 adapter는 수정하지 않았다. 1초 적분, 450초 horizon,
150초 제어 3개, 231개 미분 축, 반복 횟수·후보 수·최대 8워커를 유지한다.

## 효과가 없어 제외한 후보

아래 세 후보는 기존 143.419초 Jacobian 호출보다 빨라지지 않았다.
각각 비용·자원·두 Jacobian 차이는 0이었지만 속도 개선으로 채택하지 않았다.
그 코드와 단위 검사들은 `sources_v1`, `sources_v2`, `sources_v3`에 보존하고
실행 소스에서는 이 작업이 추가한 해당 변경만 되돌렸다.

| 후보 | 내용 | Jacobian 호출 |
|---|---|---:|
| `flow_h3_v1` | 방류 용량·경로/태그 색인 재사용 |145.758초|
| `flow_h3_v2` | 읽기 전용 집계 검사 미분 기록 제외 추가 |146.168초|
| `flow_h3_v3` | 일정한 녹색·적색 구간의 0 미분 그래프 제거 추가 |146.355초|

세 번째 후보는 그래프를 14,137,087개에서 13,395,475개로 줄였으나
미분용 교통 예측은 122.460초로 기존 121.252초보다 빨라지지 않았다.
노드 감소를 시간 개선으로 취급하지 않는다.

`functions_v1`은 150초 구간의 개별 함수 타이머다. `profile_h1_v1`은 같은
150초 길이의 scalar/tangent 두 예측을 cProfile로 계측한 진단이다.
후자의 깊은 복사 누적 13.562초 중 램프 유량 갱신 3.537초, 본선 갱신
1.806초가 제어 복사 호출에 해당했다. **계측 비용이 포함된 값**이며
이 수치를 일반 실행 시간이나 전체 결정 시간과 직접 비교하지 않는다.

## 검증 범위

계산시간 비교 기준은 기존 900초 저장 상태의 같은 망·수요·제어 기준점이다.
역사적인 이 저장 상태를 최신 native 실험의 망·수요로 치환하지 않는다.
최종 후보의 단위 검사는 수정할 사전의 분리, AD 객체 보존, 기본 OFF,
실제 METANET 방출 함수의 결과 일치와 원본 제어 불변을 확인한다.

`flow_h3_v4`의 비용·자원·두 Jacobian 차이는 모두 0이다. Jacobian 호출
145.087초, scalar 54.705초, 미분용 예측 121.359초였고 그래프 노드 수는
기존과 같은 14,137,087개다. 이때 역전파 컴파일/로드에 2.975초가 들었다.
이전 143.419초 호출은 컴파일 상태가 달라 이 비교만으로 단축 효과를 주장하지
않는다.

동일한 현재 소스에서 옵션 OFF/ON을 비교한 `states_v1`은 모든 저장 상태,
비용·자원 차이가 0이고 실행 중 소스 불변도 PASS다. 일반 예측은 OFF
56.627초, ON 55.208초로 1.419초(2.505%) 짧았다. 독립된 두 프로세스를
함께 실행한 단일 비교이며 반복 평균이나 전체 결정 시간 단축은 아니다.

## 전체 결정 결과와 채택 여부

동일한 900초 저장 상태의 전체 SDMPC 결정은 기존 **386.693초 →
387.376초(6분 27.4초)**였다. 0.683초(0.177%) 길어졌으며, 단일 측정의
이 차이로 속도 악화를 확정하지도 않는다. **전체 시간 개선은 입증하지
못했다.** 따라서 이 옵션은 실험용 OFF 기본값으로 남기고, 앞선
`sdmpc_trial_20260922/config_candidate.json`을 대체하거나 수정하지 않았다.
150초 목표는 여전히 미달이다.

- `qualification_summary.json`의 동등성·실행 무결성 23개 조건 모두 PASS다.
  이는 속도 개선 PASS를 뜻하지 않는다. 비용·자원·두 Jacobian 차이는 0이며,
  최종 원시 green·offset·8개 RM·VSL 명령, 후보 결과와 제약도 동일하다.
- 450초 예측, 3개 제어 블록, 231개 미분 축, 1초 갱신과 최대 8워커를
  유지했다. 반복 상한 2회, 실제 일반 모델 질의 6개도 같다.
- 최종 명령은 feasible이며 `iteration_limit`와 기존의 낮은 NP cap 후보
  `linear_resource_qp_failed`를 그대로 기록했다. 수렴 완료로 표현하지 않는다.
- 실행 중 소스 변경이 없었고, 사용하지 않은 선행 미분도 검증 후 모든
  소유 작업을 종료했다. 전체 저장 상태 OFF/ON의 차이도 0이다.
- 최종 SDMPC 회귀 125개 PASS, 파라미터 검사 PASS다. 기존 calibration
  우선순위 경고는 유지하며 이번 최적화 때문에 계수나 정본을 바꾸지 않았다.

현재 작은 복사·색인 변경만으로는 전체 시간을 더 줄이지 못했다. 남은 큰
비용은 차량 재고·흐름을 Python 객체로 순회하면서 미분 그래프를 구성하는
교통 예측 본체다. 다음 구조적 변경 후보는 이를 배열 기반의 수송/유량
계산과 미분 커널로 옮기는 것이며, 이 문서에서 구현 완료나 속도 이득을
주장하지 않는다.

VISSIM native 실행이나 9000초 제어 성능 개선을 검증하는 작업이 아니다.
기존 RM/VSL 순이득 보정의 NOT_QUALIFIED 상태와 과거 실패 증거는 유지한다.
설정·결과·소스 스냅샷은 `diagnostics/sdmpc_flow_updates_20260922`에 보존한다.
