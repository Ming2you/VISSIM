# SDMPC 재고·유량·미분 배열 유지 구조 검토 — 2026-09-22

판정: **다음 구현 방향으로 적절하다. 구조의 가능성은 검증했지만, 실제 전체
plant의 속도 개선은 아직 검증하지 않았다.** 이번 작업은 코드 경계 검토,
실제 저장 상태의 미분 노드 생성 위치 계측, 독립적인 작은 모형의 수명 검증이다.
운영 predictor·선택 config·vendor·VISSIM 실행은 변경하지 않았다.

## 무엇을 바꿔야 하는가

현재 `sdmpc_tangent_reverse.Trace`는 이미 전체 예측의 부모 노드와 미분
가중치를 연속 배열에 보관한다. 선택된 기존 450초 검증의 실제 역방향 순회는
약 0.992초다. 미분 행렬 계산 전체가 Python 객체인 것은 아니다.
남은 대상은 매초의 물리 상태·유량 계산에서 발생하는 `Dual` 객체, 사전/큐
순회, 자료 변환과 반복 회계다.

앞선 부분 컴파일은 한 차로군 이동 블록만 매번 배열에 옮겼다가 복원했다.
그 블록의 미분 노드는 전체의 0.446%였고, 전체 예측 시간 단축은 입증되지
않았다. 새 구조는 여러 단계가 **동일한 값·미분 참조 배열**을 직접 갱신하고,
다음 1초와 다음 150초 제어 구간에도 그 배열을 이어서 사용하는 것이다.

```text
관측 상태 → 한 번 배열화
             ↓
       [1초 물리 계산 단계들] ── 다음 1초에 같은 상태 배열 사용
             ↓                   150/300초에는 제어만 교체
       150/300/450초 독립 스냅샷
             ↓
       끝에서 기존 결과 형식으로 내보내기 + 역방향 미분
```

## 배열의 소유권과 수명

|정보|권장 저장 방식|수명 및 조건|
|---|---|---|
|망 연결·차로군·movement·회계 위치|정수 인덱스와 고정 연결 배열|정본 config에서 생성, 읽기 전용으로 재사용|
|차량 재고·속도·유량·누적 비용|각각 `float64` 값, `int64` 미분 참조, 종류 표시 배열|후보 예측마다 독립 소유, 450초 동안 유지|
|연산 미분|부모 ID 두 개와 국소 미분 가중치 두 개의 추가 전용 배열|시간 단계 사이에 기존 간선을 덮어쓰지 않음|
|목적지·초기 차량 소속·FIFO 조각|라벨 ID, 양, head/tail/next 등 가변 길이 배열|정확한 순서·차량 소속·분수 차량량 보존|
|분기·동률·불연속 의존성|이벤트와 의존 축 기록|기존 활성 분기와 제약 판정 유지|
|회계·제약 증거|시간·종류·위치 ID와 수치 열|기존 검사 시점 유지, 끝에서 읽기용 레코드 생성|
|150/300/450초 저장 상태|별도 값/참조 복사본|다음 단계의 갱신에 영향받지 않음|

물리 재고와 Ω 회계의 inside/outside 재고는 서로 다른 의미를 가진다.
같은 차량을 이중으로 TTT에 합치면 안 된다. 후보마다 가변 상태와 미분
그래프는 독립 소유한다. 8워커가 공유해도 되는 것은 검증된 읽기 전용 망
자료다. 부모 프로세스의 가변 상태를 여러 후보가 수정하게 만들지 않는다.

미분 노드 ID는 값의 고유 ID가 아니다. 기존 구현은 `x + 상수`에서 값은
바뀌어도 같은 미분 참조를 재사용한다. 그래서 상태는 항상 **값과 미분
참조를 함께** 저장해야 한다. 값 배열을 덮어쓰는 것은 가능하지만 과거
미분 간선을 덮어쓰거나 150초 경계에서 미분을 초기화해서는 안 된다.

231개 제어 축에 대한 조밀한 미분 행렬을 모든 재고·유량마다 만들 필요는
없다. 기존 역방향 방식과 호환되는 참조를 유지한다. 의존 축 표현은 별도
검토 대상이며, 현재 축 수에서는 4개의 uint64 비트셋으로 표현할 수 있다.
축 수가 바뀌면 크기도 계산해야 한다. 이 비트셋 구현은 이번에 하지 않았다.

## 코드에서 확인한 경계와 첫 구현 범위

후보 소유권 경계는 `area_runtime.evaluate_price_point`다. 여기서 후보 상태와
회계 창을 복사하고, 기존 단일 endpoint를 통해 예측한다. 배열 backend도
이 endpoint 계약을 유지해야 한다. `sdmpc_sequence`의 3개 제어 블록과
`rollout_endpoint._rollout`의 상태 스냅샷 계약도 유지한다. 별도 adapter나
endpoint 우회 경로를 만들거나 vendor를 편집하는 방식은 권하지 않는다.

`lane_coupling.run_interval`의 실제 매초 순서는 다음과 같다.

1. 램프 방출량 계산.
2. 그 방출량을 사용한 도시부 갱신 및 램프 마무리.
3. off-ramp 수용량 계산.
4. 본선 갱신 및 off-ramp 유출 계산.
5. off-ramp 도착 반영, 체류시간 적분, 재고·제약 확인.

이 순서는 배열화 후에도 동일해야 한다. 하류가 나중에 비우는 공간을
앞선 유입에 미리 쓰거나, 공유 수용량을 여러 movement가 중복 사용하면
계산이 빨라도 다른 plant가 된다. 1초 물리 갱신, 450초 horizon, 3×150초
제어, 제약·후보 수·실제 명령의 정수화 위치를 이 작업에서 바꾸지 않는다.

**첫 이식 범위는 도시부 수송의 연결된 한 계산 묶음**을 권한다.
`physical_urban_transport`와 `urban_flow_accounting` 사이의 유출 요구량,
head/receiver 수용량 배분, 실제 차량 이동, 재고 및 회계 갱신을 같은
배열에서 처리하는 범위다. 이 묶음의 중간에 `Dual`/사전으로 되돌리지 않는다.
다른 물리 영역과의 경계 유량만 명시적인 입출력으로 둔다. 여기서 기존
상태와 동등성을 증명한 후 본선·램프의 연결된 계산 묶음으로 확장한다.

FIFO는 목적지별 총량 배열 하나로 대체할 수 없다. `FIFO.take`는 앞 차량을
건너뛰지 못하지만 `take_label`은 횡방향 이동에서 뒤의 해당 라벨을 꺼낼 수
있다. 이 차이와 초기 차량 소속, 경로 라벨, 허용된 조각 병합 조건을
보존해야 한다. 배열 공간은 확장하거나 명시적으로 실패해야 하며, 부족한
공간 때문에 차량·미래 도착 예약·미분 간선을 조용히 버리면 안 된다.

`TimeBins`만 먼저 바꾸는 것은 우선순위가 낮다. 과거 상세 계측에서는
비용이 작았으며, 이미 object 배열을 사용하는 부분도 있다. 반대로 전체
legacy 객체를 매초 재구축하는 dict proxy는 객체 생성 경계를 남기므로
이번 구조의 목적을 충족하기 어렵다.

## 그래프 복원도 함께 줄여야 한다

현재 부분 커널의 `Packed.finish`는 마지막에 간선을 기존 Trace로 복사하고,
Python에서 노드마다 의존 축을 OR한다. 작은 검증 모형도 이 호환 경로를
사용했다. 이를 전체 1,413만 노드로 단순 확대하면 새 병목과 중복 메모리가
될 수 있다.

실제 backend에서는 연속 tape 버퍼에 직접 추가하거나, 단계별 버퍼를
결정된 순서로 한 번 합치는 방식과 컴파일된 의존 축 전파를 검토해야 한다.
기존 역방향 커널이 읽을 배열 형식을 유지한다. 숫자 연산 순서, 부모 간선
순서, CPython의 일반 수치 합산과 Dual 혼합 합산, min/max 동률의 선택을
보존한다. fastmath나 병렬 합산 재배열은 도입하지 않는다.

450초 기존 간선 배열은 약 452 MB이며, 새 버퍼와 복원본을 동시에 갖는
경우 이보다 더 필요하다. 8워커의 각 후보 tape와 역방향 임시 배열까지
포함한 최대 메모리는 실제 통합 후 측정해야 한다. 전체 배열화를 했다는
이유로 1초 이후 시간 단계를 서로 독립적인 워커로 병렬 실행할 수 있는
것은 아니다. 시간 의존 관계는 그대로다.

### 실제 저장 상태의 생성 위치 계측

`profile_sdmpc_array_lifetime.py`로 과거 900초 저장 상태의 첫 150초/77축만
진단했다. 운영 450초 설정은 변경하지 않았다. 2,613,091개 생성 노드 중
4,093개 간격으로 638개 호출 위치를 표본 수집했다.

|직접 호출 모듈|표본 노드 비중|
|---|---:|
|physical_urban_transport|14.89%|
|physical_lane_groups|14.89%|

이는 **CPU 시간 비중이 아니며**, 표본 간격에 따른 편향도 가능하다.
단일 함수 대신 여러 물리·회계 단계에서 노드가 생긴다는 근거로만 사용한다.

9.095e-13이다. 계측 wrapper가 포함된 실행 시간을 속도 개선 수치로
쓰지 않는다. 결과는 `node_sites_v1/result.json`, `by_file.json`이다.

### 배열 수명과 미분 연결의 독립 검증

`sdmpc_persistent_arena_probe.py`는 **실제 plant가 아닌 두 재고 모형**이다.
요구량·수용량 배분·체류비용의 세 컴파일 함수를 같은 배열 위에서 실행한다.
`check_sdmpc_persistent_arena.py`의 `lifetime_v3/result.json`에서 네 사례가
통과했다. 각 사례는 450개 시간 단계, 1,350개 함수 호출, 세 제어 블록이다.

- 150/300/450초 상태값이 기존 Python 수식과 정확히 같음.
- 미분 간선·가중치·분기/동률/불연속 기록과 전체 Jacobian이 정확히 같음.
- 상태 배열 주소 유지, tape 확장 후 과거 간선 불변, 스냅샷 불변.
- 후보 사이 메모리 독립, 비연속 시간 진행과 종료된 상태 재사용 거부.
- 질량 잔차 최대 6.47e-13. 내보내기는 예측 마지막 한 번만 수행.
- 충분한 상류 재고가 있는 사례에서 최종 상류 재고의 세 제어 미분은 모두
  -150이며, TTT 미분도 약 -15.646, -9.396, -3.146으로 모두 남음.

첫 `lifetime_v1`은 값 변경 시 반드시 새 미분 노드 ID가 있어야 한다는
잘못된 검사 때문에 실패했다. 실패 기록과 당시 소스를 보존했다. 기존
상수 덧셈 최적화를 고려하여 과거 tape 불변 검사로 바로잡은 v2는 통과했고,
세 제어 모두 최종 상태에 영향을 주는 사례를 추가한 v3도 통과했다.
실패를 통과로 덮어쓰지 않았다. 운영 코드의 수정으로 검사를 맞춘 것도 아니다.

## 적용 여부를 결정할 다음 검증

다음 구현에서 config 키 하나로 기본 OFF를 유지하고, 파라미터 검사를
통과시켜야 한다. 먼저 위 도시부 계산 묶음의 1초 출력·분기·제약·미분을
기존 경로와 비교하고, 이어 실제 저장 상태에서 450초/231축 전체 상태와
Jacobian을 대조한다. 일반 수치 후보 예측과 미분 예측 양쪽이 빨라져야 한다.
마지막으로 같은 후보·반복·명령·제약으로 전체 SDMPC 결정을 측정한다.

현재 선택된 전체 결정은 과거 단일 측정 **386.693초**다. 150초 이내가 되려면
전체 벽시계 시간을 약 61.2% 더 줄여야 한다. 이번 작은 모형의 통과는
그 단축률의 증거가 아니다. 전체 plant 이식, 새 전체 결정 벤치마크 및
VISSIM 9000초 런은 이번 검토에서 수행하지 않았다. 실제 RM/VSL 제어 이득이나
모델 정확도 검증을 이 계산 구조 검증으로 대신하지 않는다.

최종 소스 불변·선택 config SHA 검사는 `review_summary.json`에 기록한다.
