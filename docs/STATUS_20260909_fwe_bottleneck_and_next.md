# 2026-09-09 — FW_E 병목 규명, 제어 실패 원인, 다음 단계

x15 Ver2·21셀 격자에서 하루 종일 팔을 돌리고 진단했다. 결론부터: **제어가 실패한 게 아니라
모형이 이 병목을 표현할 수단을 갖고 있지 않다.** 아래는 확정된 것과 아직 열린 것, 그리고
다음에 할 일(two-branch FD 재적합)이다.

## 1. 오늘 돌린 팔

기준선: 무제어 `n21_x15_nocontrol_ver2_20260907` = **7403.9**. 시드 σ = 50.7 (1.06%).

### 1.1 세 번 재현된 지문 — 본선 모형을 조이면 도시가 좋아지고 본선이 나빠진다

```
h1 − f3    도시 −68.7   본선 +131.7   램프  +3.3
h2 − n2    도시 −17.1   본선  +93.3   램프  +7.8
i1 − n7    도시 −54.2   본선  +49.1   램프 −19.4
```

세 개의 서로 다른 개입(λ_eff 발동 ×2, two-branch)에서 방향이 같다. 컨트롤러가 "본선이 더
막힌다"고 믿으면 노력을 도시로 옮기고 순효과가 대체로 상쇄된다. **구조적 패턴이다.**

### 1.2 i1 판정 — 권한은 생겼고 방아쇠는 없다

VSL 사용은 늘었다(= 기구가 착지했다):

```
n7  셀-값 {80: 200, 120: 1102}   VSL<120 낸 결정 21/31
i1  셀-값 {80: 225, 120: 1077}   VSL<120 낸 결정 24/31
```

**그런데 붕괴 창에서는 여전히 안 쓴다.** t=900~1800 에 n7·i1 둘 다 FW_E seg5·seg8 전부 120.0
이고, 80 으로 내려가는 것은 **t=2100 부터**다 — 붕괴 개시(t≈1112) 한참 뒤다.

주목할 점: two-branch 를 켜면 ρ_c(120) = 15.16 이라 t=900 의 FW_E 최대 ρ 15.6 이 **이미 임계를
넘는다.** 그런데도 VSL 이 안 움직인다 ⇒ **임계 초과가 목적함수에서 행동으로 번역되지 않는다.**
two-branch 는 **권한**을 줬지 **방아쇠**를 주지 않았다. 남은 벽은 리더 목적함수(축 ④)와
가격(축 ⑤)이다.

**모든 rung 의 무결성은 정상**이다(37/37 결정, `SIGNAL_MIDBLOCK_COM_SKIPS=744`,
`DECISIONS_FAILED=0`).

패턴이 하나 뚜렷하다 — **METER 를 얹는 순간 +150.1 이 붙고 그 위에 무엇을 올려도 회복되지
않는다.** 아래 §3 이 그 이유다.

## 2. 병목의 정체 — 확정

### 2.1 위치와 성격

`x15` 수요 프로파일은 `freeway_mainline_input` 배수가 **0.8333** 이다(본선 수요를 오히려 83%
로 낮춘 상태). 그런데도 FW_E 가 무너지고, **무제어 런도 똑같이 무너진다.**

셀별 최초 `ρ>ρ_crit(27)` 시각 (무제어):

```
셀8 t=1350 → 셀7 1500 → 셀6 1650 → 셀5·0 1800 → 셀4 1950 → 셀2·3 2100 → 셀9 2400
셀10·11 은 시뮬 끝까지 자유류 (ρ 3~11, v 90~103)
```

* 하류가 끝까지 자유류 → **하류 spillback 아님.**
* 합류셀(셀 9 = `ramp_merge_segment_index[R_F_E]`)이 1,050 초 늦고, t=1500 엔 오히려 66 km/h
  로 회복 → **on-ramp 합류 아님.**
* 셀 8 = `off_ramp_segment_index[OR_F_E]` = **off-ramp 다이버지.**

### 2.2 차로별 실측이 지문이다

`vehicle_records.records` 의 `lane_no` 로 링크 2(FW_E 본선)를 갈라 보면:

```
t=1200 셀8  차로1 30대 20.0kph | 차로2  8대 69.8 | 차로3  3대 126.6 | 차로4  7대 104.3
t=1350 셀8  차로1 54대  7.8    | 차로2 14대 29.3 | 차로3 15대  53.5 | 차로4 16대  74.3
t=2700 셀8  차로1 72대  2.0    | 차로2 72대  2.4 | 차로3 37대  11.6 | 차로4 29대  14.9
```

붕괴 시작 시점에 **차로 1 만** 죽는데 차로 3·4 는 126·104 km/h 로 달린다. 본선 용량 붕괴면
네 차로가 같이 떨어져야 한다. 전 차로 잠김(t=2700)은 **결과**다.

### 2.3 도시부 역류도 아니다

OR_F_E 착지 커넥터 10682 는 **t=600 부터 19~23 대로 포화**한다 — 본선이 아직 완전 자유류

## 3. 왜 각 레버가 안 듣는가 — 확정

### 3.1 미터링 (세 겹으로 막혀 있다)

1. **권한 부족.** R_F_E 는 합류부 방류의 **9~12%** 만 나른다(428~571 대 2,787~5,585).
   동측 램프 수요는 430~1,300 vph 인데 cap 이 1,800 이라 **31 결정 중 2 번만 물린다.**
2. **격자 사각지대.** 팔로워의 2-램프 탐색은 **합이 고정된 배분 탐색**이다
   (`wu_faithful_follower.py:3620-3629`): `lo = max(0, budget − cap2)`, `hi = min(cap1, budget)`,
   `m2 = budget − m1`. 하한은 수요가 아니라 **상대 램프의 cap** 에서 나온다. 그리고
   `N_UF* = 7200`(31 결정 중 20 회)이면 링크 예산 = cap 합이라 `lo = hi` → **후보 1점, 탐색 없음.**
3. **가격 미분 0.** 미터 가격이 t=900~1650 전 구간 정확히 `0.000e+00`. 작동점이 cap 이고
   탐침 반경 `d_r = max(300, 0.20×1800) = 360` 이라 두 코너 롤아웃이 동일하다.
   `metering_price_trust_frac = 0.75` 로 고쳐도(g2) **−0.6** 으로 무효였다.

**편익/비용 실측**: t=900 에 R_F_E 완전 폐쇄 시 본선 TTT 절감 **0.0225 veh·h** 대 램프큐 대가
**4.98 veh·h** = **0.45%**. 자기 모형 안에서 컨트롤러의 판단이 옳다.

### 3.2 합류 교란항 δ

* `Δv = −δ·T·q_ramp·v/(L·λ_eff·(ρ+κ))`, δ=0.3. 정상상태 결손 **0.7~2.9 km/h**
  (q 428~1800). 관측은 셀별 D-lit FD 기준 **22.1 km/h**, 합류 고유 잔차 9.4 km/h → **약 20배 부족.**
* δ=0.3 은 적합값이 아니라 **격자 경계 인공물**이다 —
  `scripts/calibrate_metanet_ver2n21_20260907.py:299` 의 문헌제약 격자
  `[0.005, 0.0122, 0.05, 0.1, 0.3]` 의 최댓값이고, 자유 격자(40까지)에서는 팔 전부가 1.0~2.0 으로
  갔다. 같은 스크립트 :294-296 이 "자유 적합이 문헌 밖으로 나가면 결과가 아니라 **증상**" 이라 적어 뒀다.
* **δ 를 올리면 이중계상이다.** 합류 4셀의 셀별 `v_free` 가 42셀 중 **2·3·7·9위**로 낮다
  (평균 85.66 대 나머지 112.49). D-lit 적합이 합류 감속 26.8 km/h 를 이미 흡수했다.
* 요구 δ 가 합류셀 관측 92개에서 **0.04~420(IQR 2.1~16.4)** 로 흩어진다. δ 는 전역 스칼라이고
  셀별 표의 키에 없다 → **스칼라 하나로 못 맞춘다. 구조 문제다.**

### 3.3 VSL — 모형이 전조를 30초 만에 지운다

t=900 FW_E 셀 9(= R_F_E 합류)는 **ρ=9.2 에서 v=63 km/h** 다. 셀별 D-lit FD
(`v_free 91.31 · rho_crit 25.0 · a 2.0`)가 주는 값은 85.3 → **격차 22.1 km/h.**

어댑터는 관측 속도를 그대로 심는다(`vissim_stackelberg_adapter.py:9425`). 그런데 τ=18 s ·
T_f=10 s 라 완화 계수가 `T/τ = 0.56` 이고, **−22 km/h 편차가 3 스텝 = 30 초 만에 5 km/h 이내로
사라진다. 지평은 450 초 = 45 스텝이다.** 모형은 전조를 45 중 3 스텝만 보고 나머지는 자유류를
예측한다.

그리고 **FW_E 는 t=1200 까지 ρ_crit 을 넘지 않는다**(실제 붕괴 개시 t≈1112). 밀도 기반 방아쇠는
전부 사후에만 켜진다 — 이것이 g1(capacity drop)이 진 이유다: **회피 수단 없이 벌점만 켠 것.**

### 3.4 VSL 의 용량 권한은 **정확히 0 이다** (2026-09-09 검증)

세 사실이 겹친다.

1. **`vsl_set = [80.0, 100.0, 120.0]`** (`config_overrides.freeway_follower.vsl_set`). 바닥이 80 이다.
2. `vsl_fd_two_branch` 가 없으므로 VSL 은 순수 캡 `min(V(ρ), (1+α)·vsl)`, α=0 (`metanet.py:96`).
   지수 FD 의 유량 최대는 ρ=ρ_crit 이므로 캡 `c` 는 **`c < V(ρ_crit)` 일 때만** 용량을 깎는다.
3. FW_E 21개 셀의 `V(ρ_crit)` 은 **52.1~73.0 km/h** — **전부 80 아래.**
   셀 8(`FW_E_S8`: v_free 118.29 · ρ_crit 25.0 · a 2.0) 은 `V(ρ_crit) = 71.75`.

격자 탐색(`max_ρ ρ·min(V(ρ),c)·4`, 셀 8):

```
c=120/100/90/80 → 7174.7 veh/h  (비트 동일)
c=70 → 7170.4 (−0.06%)   c=65 → 7112.9 (−0.86%)   c=60 → 6990.8 (−2.56%)
```

**현재 vsl_set 의 어떤 값도 FW_E 어디에서도 용량을 1 veh/h 도 못 바꾼다.**

남는 채널은 송출유량 `q = ρ·v·λ` 를 줄이는 것뿐인데, **그 창도 닫혀 있다.** h1 의 31개 제어
결정에서 `v > 80`(= 80 캡이 물릴 수 있는) 결정 수:

```
셀5 6/31 · 셀6 5/31 · 셀7 3/31 · 셀8 1/31 · 셀9 0/31   |   셀10 20/31
```

셀 8 에서 캡이 물릴 수 있는 결정은 **t=900 하나**다. 그런데 컨트롤러가 seg5 에 처음 120 아래를
커밋한 시각은 **t=1800**(h1·f3 동일) — 그때 셀 8 은 이미 16 km/h. **레버가 물릴 수 있던 창과
레버를 쓴 창이 겹치지 않는다.**

**그리고 VSL 구역 1 은 셀 5–9 다.** `install_freeway_vsl_zones` 는 *i 이하의 가장 큰 머리*를
쓰므로(adapter:8371-8382) heads `[0,5,10,15]` → 구역 1 = 셀 5–9. 실측으로도 31개 결정 전부에서
`vsl.FW_E__seg5 == vsl.FW_E__seg8`. **다이버지(셀8)와 머지(셀9)가 같은 캡을 받는다** — 병목으로
유입을 조이려면 병목 자신도 같이 캡해야 하는 구조다.

## 4. off-ramp 차로폐쇄(λ_eff) — 살아 있었고, 방아쇠가 굶어 있었다

문헌식 `N_eff = (N−1) + exp[−(1/b)(n_o/(γ·n_o^max))^b]` 이 **이미 구현돼 있고 기본 ON** 이다:

* `metanet.offramp_spillback_lambda_eff` (:168-186, 주석 "Wu Eq.(22) 계열")
* `metanet.effective_lane_profile` (:189) — 리더/plant 경로
* `local_freeway_plant._local_lane_profile` (:106-119) — **팔로워 채점 경로에도 복제**
* 런타임 실효값 `enabled=True · lane_reduction=1.0 · γ=0.5 · b=2.0`
  (`default.yaml` 이 dataclass 기본 0.35 를 덮는다). `off_ramp_storage_link` 도 런타임에 채워진다
  — **config 의 빈 dict 만 보고 죽은 코드로 판단하면 틀린다.**

**고장은 방아쇠였다.** λ_eff 점유는 `OR_*_storage` 저장고 점유인데 실런 진단이
`local_observation_offramp_storage_occupancy = 0.0` 이다 — 관측 채널 `off_ramp_storage_veh` 가
**39/39 표본 전부 0**. 점유 0 → `capacity_veh <= 0` 분기 → nominal 차로 반환 → **한 번도 발동한
적이 없다.**

### 4.1 수선과 결과 (h1)

`urban.ramp.landing_storage` 로 착지 **커넥터 재차**를 저장고 점유로 심었다. 용량은 정본 규칙
(길이 × 차로수 × jam 168.18) 실측 (`outputs/offramp_landing_cap_ver2_20260909.json`):

```
OR_F_E  커넥터 10682  226.5 m × 1차로 → 38.1 veh   실측 평균 18.8 · 최대 24   포화 49%   ← 유일하게 포화
OR_D_E  10483  50.8 / 2.7 (5%)   OR_D_W  10479  43.5 / 2.2 (5%)   OR_F_W  10645  58.9 / 3.8 (6%)
```

옛 B4c 가 이중계상으로 기각된 함정은 피했다 — B4c 는 **도시 접근로** 재차를 심어 도착 seed 와
겹쳤고, 여기서는 **off-ramp 커넥터 자신**만 센다. `queue_prefix` 를 비워 정지큐 차감도 끈다
(진단 `landing_storage_queue_* = 0.0` 으로 확인).

**발동했다.** 붕괴 구간에 셀 8 에서 0.49~0.69 차로(용량 −12~17%)를 닫았고 결정도 크게 바뀌었다
(미터 29/31 · 녹색 31/31 · VSL 10/31). 그런데 결과는 **f3 대비 +59.6**, 분해하면:

```
            도시      본선     램프       합
f3        4474.1    3048.0    110.1    7632.2
h1        4405.4    3179.7    113.4    7698.5
차이       −68.7    +131.7     +3.3     +66.3
```

**도시는 68.7 좋아졌고 손실은 전부 본선이다.**

### 4.2 원인 가설 — λ_eff 가 배출까지 조인다

`metanet.py:553`:

```python
normal_off = ratio * q_values[i]        # q_values[i] = segment_flow_veh_h(rho, speed, lanes_now[i])
```

**off-ramp 배출이 셀 전체 유량의 고정 분율이고 그 유량이 λ_eff 로 깎인다.** 0.69 차로를 닫으면
빠져나가는 흐름도 17% 줄고 → 저장고가 더 안 비워지고 → λ_eff 가 더 닫힌다. **부호가 뒤집힌
양의 되먹임.** h1 의 최대 ρ 가 f3 보다 계속 높은 것(t=4800 에 135.3 대 110.0)이 그 지문이다.

물리는 반대다 — off-ramp 대기열은 **직진 차로**를 막고, 빠져나가는 흐름은 계속 흐른다.

### 4.3 그리고 처리량 제약이 아예 없다

`offramp_capacity_veh_h` 는 존재하지만 의미가 **저장 공간** 이다
(`urban_queue_model.py:499-502`: `available/horizon_h`):

```
h1 이전  cap 120,  점유 ≈ 0  → 여유 120 → flow_cap 43,200 vph  (사실상 무한)
h1 이후  cap 38.1, 점유 29   → 여유 9.1 → flow_cap  3,276 vph  (실제 유출 ~800 이라 여전히 안 물림)
```

실측한 물리는 **처리량 제약**(커넥터 ≈880 vph)인데 모형에 그걸 넣을 자리가 없다.

### 5.2 TTD 는 다른 자리에서 샌다

```
TTD = const − N(T) − L(T)      L = Σ on_ramp 도시큐 + Σ ramp_queue + off_ramp_storage + inflow_transit
```

`L` 의 넷은 **어느 저수지에도 없다.** `total_physical_vehicles` docstring 이 직접 지목한다 —
*"두 함수의 합만 쓰면 그 차량이 어느 계정에도 없다 — 4스텝 전진 후 35.46 veh 가 사라졌다."*
경화된 누출만 **≥1,072.5 veh** + 상한 없는 채널 둘. 편향 방향이 하필 **"미터를 열고 off-ramp 로
돌려라"** 로, §3 의 고장과 같은 방향이다.

**⇒ TTD 는 `−N(T)` 가 아니라 명시적 출구 누산기로 구현해야 한다.** 재료는 이미 있다:
도시 `boundary_out_sink_veh`(`urban_queue_model.py:1090`), 본선 `mainline_exit_flow_total`
(`metanet.py:784`). 둘 다 이미 구간 합산된다.

### 5.3 상류 차로감소 φ 항 — 배선은 맞고, **값이 기각된 팔의 것**이다

`Δv = −φ·T·Δλ·ρ·v²/(L·λ·ρ_cr)`, `Δλ = λ_i − λ_{i+1}` → **차로가 주는 직전 셀**에 걸린다.
이 항이 읽는 프로파일은 **λ_eff 합성본**이다(어댑터 8673 이 게시하고 8730 이 읽는다). 즉 셀 8 이
λ_eff 로 닫히면 **셀 7 에서 자동으로 발동한다. 오프바이원·부호오류 없음** — 셀 8 자신은 용량
삭감만 받고 속도항은 안 받는 교과서 배치다. **팔로워 경로에서도 산다**(`wu_distributed.py:453`
이 relaxed 분기에서 매 채점 전에 `effective_lane_profile` 을 부르고, `fw_seg_geo_rebind = 3.0`
= metanet·distributed_coordinator·wu_distributed 셋 전부 재바인딩).

**그런데 φ = 3.0 은 캘리브레이션이 기각한 값이다.**
`outputs/metanet_calibration_ver2n21_20260907.json`:

```

                           arm_results.mid2_lit.phi = 3.0   ← 패배
```

그런데 라이브가 읽는 `outputs/freeway_segment_params_dlit_20260908.json` 의 `dynamics` 블록이
**패배한 mid2_lit 팔의 것 그대로**다. 캘리브레이션 로그 다섯 벌에서 승리 팔은 다섯 번 다

* **지배 발화점은 셀 7 이 아니라 셀 12 다.** h1 런에서 재계산한 Δv 평균: 셀 12(정적 4→3)

## 7. 다음 단계 — two-branch FD 재적합

### 7.1 왜 이것인가

MPC-VSL 문헌의 표준 구성은 **VSL 이 임계밀도를 옮기는 FD** 다. 그래야 "VSL 로 breakdown 을
피한다"가 성립하고, capacity drop 이 벌점이 아니라 **회피 가능한 벌점**이 된다. 우리는
`vsl_fd_two_branch` 가 꺼져 있어 `effective_rho_crit` 이 고정 `net.rho_crit` 을 돌려준다
(`metanet.py:65`). 지금 우리 VSL 은 `min(V(ρ), vsl)` 짜리 순수 속도상한이라 **문헌 기구가 없다.**

오늘 진 팔들은 전부 **지름길**이었다:

| 팔 | 실제로 뭘 테스트했나 |
|---|---|
| g1 CAPDROP | 회피 수단 없이 벌점만 → 예상대로 손해 |
| g2 +PROBE | 애초에 물리지 않는 미터의 가격을 고침 |
| h1 LANDING | 병목을 보이게는 했으나 §4.2 부호 오류 동반 |
| f3·f4 METER | 권한이 9~12% 인 레버 |

**문헌 구성은 한 번도 돌리지 않았다.**

### 7.2 무엇을 적합해야 하는가

vendor 구현(`metanet.py:18-68`)이 요구하는 것:

```
two_branch_vsl_speed_kmh(rho, v_free, rho_crit, rho_jam, vsl)
  ρ ≤ ρ_c(vsl):  v = vsl                                   (자유류 branch = VSL 로 회전)
  ρ >  ρ_c(vsl):  v = w·(ρ_jam − ρ)/ρ                       (혼잡 branch 고정)
  w      = v_free·ρ_crit_tb /(ρ_jam − ρ_crit_tb)            고정 backward-wave
  ρ_c(vsl) = w·ρ_jam /(vsl + w)                             VSL↓ → ρ_c↑
```

필요한 새 값 둘:

* **`rho_crit_two_branch`** — 삼각형 FD 의 nominal 임계밀도. docstring 이 경고한다:
  *"삼각형 capacity = v_free·rho_crit 이라 exponential 용 rho_crit 을 그대로 쓰면 capacity 가
  뻥튀기된다."* 지금 값으로 그냥 켜면 용량이 **1.87배** 부푼다.
* **`rho_max`(= ρ_jam)** — 혼잡 branch 의 앵커. 현재 config 의 `network` 절에 **없다**.

### 7.3 적합 계획 (무제어 런 기반)

데이터: `evaluation/runs/n21_x15_nocontrol_ver2_20260907/decisions_*/state_*.json`
— 37 상태 × 42 셀 = **1,554 개 (ρ, v) 표본**. 셀별 `count / (length_km × lanes)` 와
`speed_sum / count`, 그리고 `q = speed_sum / length_km`.

무제어 런을 쓰는 이유: VSL 이 전 구간 120 이라 **자유류 branch 가 v_free 로 앵커된 순수 관측**
이고, 제어 런의 VSL 개입이 FD 를 오염시키지 않는다.

절차:

1. 셀별로 (ρ, q) 산점을 만들고 **자유류/혼잡 분지를 분리**한다(전환점 = q 최대 근방).
2. 혼잡 분지에 `q = w·(ρ_jam − ρ)` 를 적합해 **w 와 ρ_jam** 을 얻는다.
   (혼잡 표본은 충분하다 — FW_E 셀 0~8 이 t=1350 이후 계속 ρ 100 이상이다.)
3. `ρ_crit_tb = w·ρ_jam/(v_free + w)` 로 역산하고, 삼각형 용량 `v_free·ρ_crit_tb` 가 실측 방류
   상한과 맞는지 검산한다.
4. 셀별 D-lit 표(`fw_seg_param_segments = 42`)가 이미 무장돼 있으므로 **셀별로** 낸다.
   다만 어댑터 `_keys`(:8206-8207)에 `rho_max` 는 있고 `rho_crit_two_branch` 는 **없다** —
   확장이 필요한지 먼저 확인한다.
5. 관측 ρ 가 130 을 넘는 셀이 있으므로(t=3600 FW_E 최대 128~135) **ρ_jam 이 그보다 커야 한다.**
   현재 벤더 값 95.02 로는 CTM receiving 이 음수가 된다.

### 7.4 검증 관문 (돌리기 전)

1. `verify_parameters.py` PASS.
2. 오프라인으로 `effective_rho_crit(net, vsl)` 를 vsl 60~120 에 대해 찍어 **ρ_c 가 실제로
   올라가는지** 확인.
3. 삼각형 용량 `v_free·ρ_crit_tb` 대 기존 `freeway_capacity_veh_h = 6937` 비교 — 1.87배 부풂이
   해소됐는지.
4. 첫 결정(t=900)이 통과하는지 감시 (오늘 `config_overrides.network` 에 주석 키를 넣어
   `NetworkConfig.__init__() got an unexpected keyword` 로 런을 한 번 버렸다 — 그 절은
   데이터클래스로 언팩된다).

### 7.5 팔 설계

분기는 **n2(SPILL+RL) = 7346.5** — 무제어를 이기는 유일한 기반이고, METER 오염이 없다.

```
i1 = n2 + two-branch FD (재적합값) + vsl_set 에 60·70 추가
i2 = i1 + capacity_drop_discharge_phi = 0.85      ← 문헌 구성(회피 수단 + 벌점)을 처음으로 완성
```

φ_discharge 를 **단독으로** 켜면 g1 처럼 진다. **반드시 two-branch 와 짝으로** 올린다.
그리고 two-branch 없이도 vsl_set 확장은 필요하다 — §3.4 대로 지금 set 은 **용량 권한이 0** 이다.

| N5 | 팔로워 점유 동결 해제 (§5.4) | 코드 | 되먹임을 팔로워 안에서 닫는다. two-branch 를 켜도 이게 없으면 후보가 λ_eff 를 못 움직인다 |
| N6 | off-ramp 처리량 cap (§4.3) + λ_eff 를 직진 몫에만 (§4.2) | 코드 | h1 이 본선을 +131.7 나쁘게 만든 부호 오류 |

**N1~N4 는 오늘 밤 안에 판정이 난다.** two-branch 적합(§7.2~7.4)은 그 다음이다 —
N4 가 "용량 권한이 생기면 쓴다"를 보여주면 two-branch 의 기대치가 훨씬 명확해진다.
